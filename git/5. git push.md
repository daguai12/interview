好的，`git push` 是 Git 工作流中与 `git fetch` / `git pull` 相对的核心命令。

  * `git fetch` / `git pull` 是\*\*“下载”\*\*（从远程仓库拉取到本地）。
  * `git push` 则是\*\*“上传”\*\*（将本地的提交推送到远程仓库）。

`git push` 是您**分享工作**和**备份代码**的主要方式。当您在本地完成了一系列提交（`git commit`），您需要用 `git push` 才能将这些“存档点”上传到 GitHub、GitLab 等远程服务器上，这样您的同事才能看到您的代码。

### `git push` 的基本语法

最完整的语法是：
`git push <远程仓库别名> <本地分支名>:<远程分支名>`

不过，99% 的情况下，您会使用它的简化版：
`git push <远程仓库别名> <本地分支名>`

  * **`<远程仓库别名>`**：就是您用 `git remote -v` 看到的那个名字，**通常是 `origin`**。
  * **`<本地分支名>`**：您想要推送的您本地的分支，比如 `main` 或者 `feature/login`。

-----

### 场景一：最常规的推送（最常用）

**目标**：您在本地的 `main` 分支上完成了一个新提交，想把它推送到 `origin` 仓库的 `main` 分支上。

**详细案例：**

1.  **本地工作**：您修改了文件，并创建了一个新提交 C3。

      * **本地历史**： `(C1) -> (C2) -> (C3) <-- main`
      * **远程历史**： `(C1) -> (C2) <-- origin/main` (远程还不知道 C3 的存在)

2.  **执行推送**：

    ```bash
    # 语法: git push <远程名> <本地分支>
    $ git push origin main
    ```

3.  **查看结果**：
    Git 会显示类似这样的信息：

    ```bash
    Enumerating objects: 5, done.
    Counting objects: 100% (5/5), done.
    ...
    Writing objects: 100% (3/3), 280 bytes | 280.00 KiB/s, done.
    Total 3 (delta 1), reused 0 (delta 0)
    To https://github.com/user/repo.git
       a1b2c3d..e7f8g9h  main -> main
    ```

      * `a1b2c3d..e7f8g9h`：表示远程的 `main` 分支的“书签”从 `a1b2c3d` (C2) 被**更新**到了 `e7f8g9h` (C3)。
      * `main -> main`：表示您本地的 `main` 分支成功推送到了远程的 `main` 分支。

4.  **最终状态**：

      * **本地历史**： `(C1) -> (C2) -> (C3) <-- main`
      * **远程历史**： `(C1) -> (C2) -> (C3) <-- origin/main` (现在同步了)

-----

### 场景二：第一次推送新分支 (设置上游跟踪)

**目标**：您在本地创建了一个**新**分支 `feature/login`，现在是**第一次**把它推送到 `origin`。

**详细案例：**

1.  **本地工作**：

    ```bash
    $ git switch -c feature/login
    ... (工作并提交) ...
    ```

2.  **执行推送（常规方式）**：

    ```bash
    $ git push origin feature/login
    ```

    这能成功。但是，Git 会给您一个有用的提示：

    ```bash
    ...
    To https://github.com/user/repo.git
     * [new branch]      feature/login -> feature/login
    Branch 'feature/login' set up to track remote branch 'feature/login' from 'origin'.
    ```

    (旧版 Git 可能不会自动设置，需要您手动操作)

3.  **执行推送（最佳实践：使用 `-u`）**：
    在第一次推送新分支时，我们推荐使用 `-u` (或 `--set-upstream`) 标志。

    ```bash
    $ git push -u origin feature/login
    ```

      * **`-u` 做了什么？**
        它在推送的同时，还做了一件额外的事：在本地设置 `feature/login` 分支去“**跟踪**” (track) `origin/feature/login` 分支。
      * **为什么要这样做？（为了偷懒）**
        一旦设置了“跟踪”，`feature/login` 就和 `origin/feature/login` “绑定”了。从现在开始，当您在这个分支上时：
          * 您只需要输入 `git push`（Git 自动知道您想推送到 `origin/feature/login`）。
          * 您只需要输入 `git pull`（Git 自动知道您想从 `origin/feature/login` 拉取）。
          * `git status` 会明确告诉您“您领先/落后远程分支 X 个提交”。

### 场景三：推送失败（最需要理解的场景）

**目标**：您尝试 `git push`，但 Git 拒绝了您，提示 `(non-fast-forward)`。

**这是 Git 中最常见的“冲突”之一。**

**发生时机**：在您准备推送您的提交 (C3) 之前，您的同事**已经**向远程仓库推送了别的提交 (C4)。

**详细案例：**

1.  **初始状态**：您和远程都基于 C2。

      * **本地历史**： `(C1) -> (C2)`
      * **远程历史**： `(C1) -> (C2)`

2.  **各自工作**：

      * 您在本地提交了 `C3`：`(C1) -> (C2) -> (C3) <-- main`
      * 您的同事推送了 `C4`：`(C1) -> (C2) -> (C4) <-- origin/main`

3.  **执行推送**：
    您（不知道 C4 的存在）兴高采烈地去推送您的 C3：

    ```bash
    $ git push origin main
    To https://github.com/user/repo.git
     ! [rejected]        main -> main (non-fast-forward)
    error: failed to push some refs to 'https://github.com/user/repo.git'
    hint: Updates were rejected because the remote contains work that you do
    hint: not have locally. This is usually caused by another repository pushing
    hint: to the same ref. You may want to first integrate the remote changes
    hint: (e.g., 'git pull ...') before pushing again.
    ```

4.  **解读错误**：

      * `! [rejected]`：推送被拒绝。
      * `(non-fast-forward)`：**“非快进”**。这是核心原因。
      * **Git 在保护您！** Git 告诉您：“等等！您本地的 C3 是基于 C2 的。但远程的最新版已经是 C4 了。如果我允许您推送 C3，远程的 C4 就会**被覆盖并丢失**！我不能这么做。”
      * **当前历史（分叉状态）**：
        ```
                              (C3)  <-- 您的 main (您想推送这个)
                             /
        (C1) -> (C2) -> (C4)  <-- origin/main (远程已经是这个)
        ```

5.  **标准解决方案（Fetch + Rebase/Merge）**：
    Git 提示您了：`you may want to first integrate the remote changes` (您应该先合并远程的更改)。

      * **步骤 1：`git fetch origin`**
        （就是您上节课学的！）先把 C4 下载到本地的 `origin/main` 书签上。
      * **步骤 2：`git rebase origin/main`** (推荐)
        （就是您上上节课学的！）把您的 C3 “嫁接”到 C4 之后，变成 `C3'`。
          * **变基后本地历史**：`(C1) -> (C2) -> (C4) -> (C3') <-- main`
      * **步骤 3：`git push origin main`**
        现在再推送。Git 发现您本地的 `main` (C3') 是基于远程的 `main` (C4) 的，这是一个“快进”(Fast-Forward) 操作。
      * **推送成功！**

-----

### 场景四：强制推送 (危险，但有时必须)

**目标**：您**故意**重写了本地的历史（比如用了 `git rebase -i` 清理了提交），现在您想强制用您的本地版本覆盖远程版本。

**详细案例：**

1.  **本地历史**： `(C1) -> (C2) -> (C3)`

2.  **远程历史**： `(C1) -> (C2) -> (C3)` (您之前推过了)

3.  您在本地执行了 `git commit --amend` 或 `git rebase -i`，把 C3 修改成了 `C3'`。

      * **本地历史**： `(C1) -> (C2) -> (C3') <-- main`

4.  您尝试 `git push`，Git 会**拒绝**您（和场景三一样的 `non-fast-forward` 错误），因为 `C3'` 和 `C3` 是两个不同的提交。

5.  **执行强制推送**：
    **警告：** 强制推送会**永久覆盖**远程仓库的历史。请**100%确认**没有别人在基于旧的 `C3` 提交工作！**永远不要对 `main` 这样的共享分支强推！**

    ```bash
    # (不推荐，太粗暴)
    $ git push --force origin main

    # (推荐！更安全的强推)
    $ git push --force-with-lease origin main
    ```

      * `--force-with-lease` (带租约的强推)：它更智能。它会检查一下：“远程的 `main` 还是我上次 `fetch` 时看到的 `C3` 吗？如果是，我就覆盖它。如果在我 `fetch` 之后，又有别人（比如张三）推送了 `C4`，那我就**失败**。” 这能防止您覆盖掉张三的工作。

-----

### 场景五：删除远程分支

**目标**：您的 `feature/login` 分支已经合并回 `main` 了，您想删除远程的 `feature/login` 分支。

  * **命令（新版，易于记忆）**：
    `git push origin --delete <branch-name>`

  * **命令（旧版，语法诡异）**：
    `git push origin :<branch-name>`
    （推送一个“空”到远程分支，即删除它）

**详细案例：**

```bash
$ git push origin --delete feature/login
To https://github.com/user/repo.git
 - [deleted]         feature/login
```

-----

### 总结：`git push` 速查表

| 您的意图 | 命令 | 解释 |
| :--- | :--- | :--- |
| **常规推送** | `git push origin main` | 推送本地 `main` 到远程 `origin/main` |
| **首次推送** | `git push -u origin feature` | 推送新分支，并设置“跟踪” |
| **偷懒推送** | `git push` | （需先设置 `-u`）推送当前分支到其跟踪的远程分支 |
| **推送失败** | `! [rejected]` | (non-fast-forward) 错误 |
| **解决失败** | 1. `git fetch` 2. `git rebase` 3. `git push` | 专业的“推-拉”工作流 |
| **强制推送** | `git push --force-with-lease origin feature` | **(有风险)** 用本地历史覆盖远程（`rebase` 之后常用） |
| **删除远程分支** | `git push origin --delete feature` | 清理已合并的分支 |
| **推送所有标签** | `git push --tags` | `push` 默认不推送标签，需额外执行此命令 |
