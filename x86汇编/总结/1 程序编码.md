### 核心总结：从 C 代码到可执行文件的过程

文档的核心内容是描述了 C 语言源文件（如 `p1.c` 和 `p2.c`）通过 `gcc` 命令转变为一个可执行文件（如 `p`）所经历的四个关键阶段：

1.  **预处理 (Preprocessing)**：处理 `#include`（导入头文件）和 `#define`（替换宏）。
2.  **编译 (Compilation)**：将 C 代码（`.c`）翻译成汇编代码（`.s`）。
3.  **汇编 (Assembly)**：将汇编代码（`.s`）翻译成二进制的**目标代码**（`.o`）。
4.  **链接 (Linking)**：将一个或多个目标代码（如 `p1.o`, `p2.o`）与所需的库函数（如 `printf`）合并，生成最终的**可执行代码**（`p`）。

### 关键知识点讲解

#### 1\. 什么是目标代码 (Object Code)？

目标代码（`.o` 文件）已经是机器代码了，但它还不完整。

以文档中的 `mstore.c` 示例来看，当它被汇编成 `mstore.o` 后，我们使用 `objdump` 查看它的机器代码：

```
0000000000000000 <multstore>:
   0:   53                      push   %rbx
   ...
   4:   e8 00 00 00 00          callq  9 <multstore+0x9> 
   ...
```

注意 `callq` 这一行。它要调用 `mult2` 函数，但此时汇编器并不知道 `mult2` 函数的最终地址在哪里（它可能在另一个 `.o` 文件或库中），所以它暂时填了一个相对地址（`00 00 00 00`）。

#### 2\. 链接器 (Linker) 做了什么？

链接器的作用就是“解决”目标代码中的不完整之处。文档通过对比 `mstore.o` 和可执行文件 `prog` 的反汇编代码，清晰地展示了链接器的两大工作：

1.  **地址重定位 (Relocation)**：
      * 在 `mstore.o` 中，`multstore` 函数的地址是从 `0` 开始的。
      * 在可执行文件 `prog` 中，链接器为它分配了一个最终的虚拟内存地址，比如 `400540`。
2.  **符号解析 (Symbol Resolution)**：
      * 在 `mstore.o` 中，`callq` 指令不知道 `mult2` 的地址。
      * 在 `prog` 中，链接器找到了 `mult2` 函数的地址（比如 `40058b`），然后**把这个真实地址填回**到了 `callq` 指令中（`e8 42 00 00 00`）。

#### 3\. C 语言与机器代码的区别

文档指出了 C 语言和机器代码的几个关键区别：

  * **抽象层次不同**：C 语言隐藏了处理器的细节。而机器级代码会直接暴露出处理器的状态，例如：
      * **程序计数器 (`%rip`)**：指向下一条要执行的指令地址。
      * **寄存器**：用于存储临时数据或指针。
      * **条件码寄存器**：用于实现 `if` 或 `while` 循环等判断。
  * **数据类型不同**：C 语言有 `int`, `struct`, 数组等丰富的数据类型。在机器代码层面，它们都只是连续的字节块，机器代码本身不区分有符号/无符号整数，也不区分指针和整数。

#### 4\. 汇编格式：ATT vs. Intel

这是一个非常重要且容易混淆的点。GCC 默认使用 **ATT 格式**，而 Intel 和微软的文档使用 **Intel 格式**。它们的主要区别是：

  * **操作数顺序相反**：这是最关键的区别。
      * **ATT (GCC)**: `movq %rax, %rbx` (源 -\> 目标)
      * **Intel**: `mov rbx, rax` (目标 -\> 源)
  * **其他区别**：ATT 格式用 `％` 作寄存器前缀（`%rbx`），Intel 则不用（`rbx`）；ATT 使用后缀（`movq`）表示操作数大小，Intel 则省略。
