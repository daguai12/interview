好的，咱们来聊聊第七章的动态链接。想象一下，静态链接就像是把所有家具（代码模块、库）都焊死在你的房子（可执行文件）里，虽然结实，但搬家、换家具都巨麻烦，而且每家都这么搞，太占地方了。动态链接就是一种更现代、更灵活的“装修”方式。

**1. 为啥要动态链接？（静态链接的痛点）**

* **太占地儿**：静态链接下，像 `printf` 这种常用函数，每个程序里都得带一份完整的副本。如果系统里有一千个程序都用了 `printf`，那内存和硬盘里就有一千份几乎一样的代码，纯属浪费。
* **更新噩梦**：如果 `printf` 函数发现了个 bug 需要修复，静态链接下，所有用到它的程序都得**重新编译链接**一遍，然后整个程序重新发布。用户就得下载一个可能很大的完整程序，太折腾了。
* **动态链接来拯救**：基本想法就是，别在编译时就把所有东西“焊死”。程序运行时，需要哪个库（比如 C 库 `libc.so`），**当场**把它加载到内存里，然后把程序里调用 `printf` 的地方指向内存里那**唯一一份** `printf` 代码。
    * **优点**：
        * **省空间**：库文件在磁盘和内存里通常只需要一份，大家共享。
        * **易更新**：修复了 `libc.so` 的 bug，直接替换这个文件就行，下次程序运行时自动加载新版本，程序本身不用动（理想情况下）。
        * **模块化/插件**：程序可以在运行时决定加载哪个模块，实现插件功能。
        * **兼容性**：提供一层抽象，程序可能更容易在不同系统版本上运行。
    * **缺点**：
        * **依赖地狱 (DLL Hell)**：如果新版库的接口和旧版不兼容（比如删了个函数），依赖旧版的程序就可能崩溃。
        * **性能**：运行时需要做链接工作，访问外部函数/变量需要多一层“中转”，比静态链接稍微慢一点点（通常影响不大）。

**2. 简单感受一下过程**

1.  **准备**：我们把 `Lib.c` 编译成一个共享的“零件” `Lib.so` (用 `gcc -fPIC -shared ...`)。
2.  **“预定”链接**：编译主程序 `Program1.c` 时，告诉链接器：“我将来需要 `Lib.so` 里的东西”（`gcc -o Program1 Program1.c ./Lib.so`）。链接器这时**并不会**把 `Lib.so` 的代码拷进 `Program1`，它只是检查一下 `Lib.so` 里确实有 `Program1` 需要的函数（比如 `foobar`），然后在 `Program1` 里做个标记：“这里的 `foobar` 调用将来要去动态库里找”。
3.  **运行时“现场组装”**：
    * 操作系统加载 `Program1`。
    * 发现 `Program1` 需要 `Lib.so`（根据之前的标记）。
    * 加载一个叫**动态链接器**（比如 `ld-linux.so`）的“总管”。
    * 动态链接器负责加载 `Lib.so` 到内存（如果还没加载的话）。
    * 动态链接器把 `Program1` 里调用 `foobar` 的地方，指向内存里 `Lib.so` 中 `foobar` 函数的实际地址。
    * 所有“预定”的链接都完成后，动态链接器才把控制权交给 `Program1` 的入口，程序开始跑。
4.  **内存布局**：这时候看进程的内存，里面不仅有 `Program1` 的代码和数据，还有 `Lib.so`、C 库 (`libc.so`) 以及动态链接器自己的代码和数据。

**关键点**：`Lib.so` 加载到内存的**具体地址**在编译时是不知道的，是运行时动态链接器找个空地儿放进去的。

**3. 地址不确定怎么办？—— 地址无关代码 (PIC)**

既然共享库 `.so` 加载地址不固定，那库内部的代码怎么访问自己的全局变量或者调用自己的其他函数呢？如果代码里写死了绝对地址，一旦加载地址变了，不就全乱套了吗？

* **笨办法（不好）：加载时重定位**。就像早期没有虚拟内存时一样，加载时发现地址变了，就把代码里所有用到绝对地址的地方都改一遍（加上地址偏移量）。**缺点**：改过的代码就不能在多个进程间共享了，违背了动态链接省内存的初衷。
* **妙招（好）：地址无关代码 (PIC - Position-Independent Code)**。核心思想是：让**代码段**本身不包含任何需要修改的绝对地址，无论加载到哪里都能直接运行。怎么做呢？把地址相关的部分“挪”到**数据段**里去！
    * **访问内部函数/跳转**：用**相对地址**。比如 `call` 指令跳转的目标是“往前 50 字节”，这跟加载到哪儿没关系。
    * **访问内部数据**：稍微麻烦点。代码先想办法获取**当前指令的地址 (PC)**，然后加上一个**固定的偏移量**去访问数据（因为代码和数据在模块内的相对位置是固定的）。
    * **访问外部数据**（别的模块定义的全局变量）：在自己的数据段里创建一个**全局偏移表 (GOT - Global Offset Table)**。GOT 就像一个地址簿，里面预留了条目准备存放外部变量的实际地址。代码先通过相对偏移找到 GOT，然后从 GOT 里查到外部变量的真正地址再去访问。动态链接器在加载时会负责把正确的地址填到 GOT 里。
    * **调用外部函数**：类似访问外部数据，可以通过 GOT 间接跳转。但更常用的是下面要说的 PLT 技术。
    * **编译开关**：用 `gcc -fPIC ...` 来生成这种地址无关代码。

**4. 懒人福音 —— 延迟绑定 (PLT)**

程序启动时，动态链接器需要解析所有外部符号（函数、变量）的地址。如果程序很大，依赖的库很多，这个过程可能很耗时。但很多函数可能整个程序运行下来一次都没被调用过！一开始就把它们地址全解析好，有点浪费。

* **延迟绑定 (Lazy Binding)**：干脆偷个懒！只有当一个外部函数**第一次**被实际调用时，才去查找它的地址并“绑定”。
* **过程链接表 (PLT - Procedure Linkage Table)**：为了实现这个“懒加载”，ELF 设计了一个叫 PLT 的“中转站”。
    1.  程序代码调用外部函数 `func` 时，实际上是跳转到 PLT 表里 `func` 对应的条目 `func@plt`。
    2.  `func@plt` 干的第一件事是跳转到 `.got.plt` 表里 `func` 对应条目 `func@GOT` 里存的地址。
    3.  **第一次调用时**：`func@GOT` 里存的**不是** `func` 的真正地址，而是 `func@plt` 里一段特殊代码的地址（通常是 `push n; jump resolver`）。于是，执行这个跳转等于没跳，接着执行特殊代码。
    4.  这段特殊代码会把 `func` 的一些信息（比如符号索引 `n`）压栈，然后跳转到**动态链接器的解析函数**（比如 `_dl_runtime_resolve`）。
    5.  解析函数干活：查找 `func` 的真正地址，然后**把这个真地址写回到 `func@GOT` 里**，覆盖掉原来的特殊代码地址。最后，跳转到 `func` 的真正地址去执行。
    6.  **以后再调用时**：程序还是先跳到 `func@plt`，`func@plt` 再跳到 `func@GOT` 存的地址。但这时 `func@GOT` 里已经是 `func` 的真正地址了！于是直接就跳转到 `func` 执行了，不再需要动态链接器介入。

这样，只有第一次调用会慢一点（需要解析），后续调用就几乎和静态链接一样快了。

**5. 动态链接的“户口本” —— 相关 ELF 结构**

ELF 文件里专门有一些段用来支持动态链接：

* **`.interp` 段**：非常简单，里面就存了一个字符串，指明需要哪个**动态链接器**来“伺候”它（比如 `/lib/ld-linux.so.2`）。
* **`.dynamic` 段**：这是动态链接的“核心控制室”。里面是一堆条目，记录了各种信息：
    * 依赖哪些共享库 (`DT_NEEDED`)。
    * 动态符号表 (`.dynsym`)、字符串表 (`.dynstr`)、重定位表 (`.rel.dyn`, `.rel.plt`) 的地址。
    * 初始化 (`.init`) 和结束 (`.fini`) 函数的地址。
    * GOT 表的地址。
* **`.dynsym` 段**：动态符号表。只包含**导入**和**导出**的符号，不包含模块内部的局部符号（`.symtab` 可能包含所有符号）。
* **`.dynstr` 段**：配合 `.dynsym` 用的字符串表。
* **`.hash` / `.gnu.hash` 段**：为了让动态链接器快速查找符号（比如根据名字找地址），搞了个哈希表。
* **`.rel.dyn` 和 `.rel.plt` 段**：动态重定位表。记录了运行时需要修正地址的位置（主要是 GOT 条目和数据段里的绝对地址引用）。

**6. 动态链接全过程**

动态链接器（比如 `ld-linux.so.2`）在程序启动时都干了些啥？

1.  **自举 (Bootstrap)**：动态链接器自己也是个共享对象，但它不能依赖别人。所以它得先“自己动手”，完成对自己内部全局变量等的重定位，这个过程叫自举。
2.  **加载共享对象**：根据主程序 `.dynamic` 段里的 `DT_NEEDED` 列表，递归地把所有需要的共享库都加载（`mmap`）到内存里。
3.  **符号解析/地址绑定**：遍历所有加载进来的模块的符号表，建立一个全局的符号查找表。**注意**：如果不同模块定义了同名的全局符号，通常是**第一个加载的模块优先**（后面的同名符号会被忽略），这叫**全局符号介入**。
4.  **重定位**：根据每个模块的动态重定位表 (`.rel.dyn`, `.rel.plt`)，把所有需要修正的地址（比如 GOT/PLT 里的条目，数据段里的绝对地址引用）填上正确的运行时地址。
5.  **运行初始化代码**：执行所有加载进来的共享库的 `.init` 段代码（如果有的话）。
6.  **交接控制权**：所有工作完成，动态链接器把 CPU 控制权交给主程序的入口点（`e_entry`），程序正式开始运行。

**7. 随叫随到 —— 显式运行时链接 (插件机制)**

除了程序启动时自动加载依赖库，我们还可以在程序运行过程中，**手动**加载和卸载共享库。这常用来实现插件（Plugins）或驱动程序。

* **Linux API**：
    * `dlopen()`：传入库文件名，加载库，返回一个“句柄”。可以指定是立即解析所有符号 (`RTLD_NOW`) 还是延迟绑定 (`RTLD_LAZY`)。
    * `dlsym()`：传入句柄和符号名（字符串），查找该符号在库（及其依赖库）中的地址。
    * `dlerror()`：如果上面的函数出错了，用它来获取错误信息。
    * `dlclose()`：传入句柄，卸载库（基于引用计数，计数为 0 才真卸载）。
* **挑战**：`dlsym` 只返回一个地址 (`void*`)，我们并不知道这个地址对应的函数到底需要几个参数、什么类型、返回值是什么。所以，通常需要调用者事先知道函数的**签名**，然后把返回的地址强制转换成对应的函数指针类型才能安全调用。像 `runso` 例子那样通过命令行指定类型，然后用汇编构造调用栈是一种比较 Hack 但可行的方法。

**总结**：动态链接通过推迟链接过程到运行时，解决了静态链接的空间浪费和更新难题，核心技术是地址无关代码 (PIC) 和用于间接寻址/延迟绑定的 GOT/PLT 机制。ELF 文件通过 `.interp`, `.dynamic`, `.dynsym` 等特殊段来支持这个过程，由动态链接器负责具体的加载、符号解析和重定位工作。此外，显式运行时链接提供了更大的灵活性，是实现插件等功能的基础。
