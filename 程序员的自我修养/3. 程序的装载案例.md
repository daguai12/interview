**例子 1：看看进程的“家”长啥样 —— 虚拟地址空间**

想象我们运行了一个简单的 C 程序，比如就叫 `my_program`。在 Linux 下，我们可以用 `cat /proc/<pid>/maps` （`<pid>` 换成 `my_program` 的进程号）来偷窥它的虚拟地址空间布局，可能会看到类似这样的输出（地址和文件名会变化）：

```
08048000-0804c000 r-xp 00000000 08:01 12345   /home/user/my_program  <-- 代码段 (Text Segment)
0804c000-0804d000 rw-p 00003000 08:01 12345   /home/user/my_program  <-- 数据段 (Data/BSS Segment)
0804d000-0806e000 rw-p 00000000 00:00 0       [heap]                   <-- 堆 (Heap)
... (可能还有其他映射) ...
b7e00000-b7f8c000 r-xp 00000000 08:01 67890   /lib/libc.so.6           <-- C库的代码段
b7f8c000-b7f8f000 rw-p 0018b000 08:01 67890   /lib/libc.so.6           <-- C库的数据段
... (可能还有动态链接器 ld-linux.so 等) ...
bfc00000-bfc15000 rw-p 00000000 00:00 0       [stack]                  <-- 栈 (Stack)
c0000000-ffffffff ---p 00000000 00:00 0                                <-- 内核空间 (Kernel Space, 用户不可访问)
```

  * **用户 vs 内核**：看到 `c0000000` 以上的地址了吗？那是内核的地盘，咱们的用户程序碰不了。下面的是用户空间。
  * **段的映射**：`08048000` 开始那两行就是 `my_program` 这个可执行文件被映射进来的地方。第一行 `r-xp` 表示只读、可执行，对应代码段；第二行 `rw-p` 表示可读写，对应数据段和 BSS 段。
  * **堆和栈**：看到 `[heap]` 和 `[stack]` 了吗？它们没有对应的文件名，是“匿名”的内存区域，操作系统直接分配的。堆通常在数据段之上，往高地址长；栈通常在用户空间顶部，往低地址长。
  * **共享库**：`/lib/libc.so.6` 也被映射进来了，因为它被 `my_program` 依赖。注意它也有自己的代码段和数据段。

**例子 2：需要才拿 —— 页错误 (Page Fault) 的比喻**

想象你去图书馆（内存）看一本很厚的书（程序）。

1.  **登记借阅 (建立映射)**：你先去前台查书目卡片（可执行文件头），管理员（操作系统）告诉你这本书放在第 5 排书架第 3 层（虚拟地址），并在你的借阅证（进程 VMA 数据结构）上登记好：“这本书应该在这个位置”。**但是**，他并没立刻把书给你拿过来。
2.  **翻到那一页 (访问内存)**：你回到座位，想看第 100 页（访问虚拟地址 `0x08048100`）。你低头一看，手里是空的！
3.  **找管理员要书 (发生页错误)**：你举手：“管理员！我登记的这本书第 100 页还没给我！”（CPU 触发页错误，通知操作系统）。
4.  **管理员取书上架 (处理页错误)**：管理员根据你的借阅证记录，跑到库房（硬盘）找到这本书，把包含第 100 页的那一卷（物理页面）拿出来，放到你面前的书架空位上（分配物理内存页），并在借阅证上记下：“第 5 排书架第 3 层现在对应你面前这个书架位”（建立虚拟页到物理页的映射）。
5.  **继续阅读 (恢复执行)**：管理员说：“好了，书来了，你继续看吧。”（操作系统返回，CPU 重新执行刚才访问第 100 页的指令），这次你就能看到了。

以后你要看第 101 页，因为还在同一卷书里，就直接看了。如果要看第 500 页，可能又需要重复 2-5 的过程去拿另一卷书。

**例子 3：“打包”加载 —— Segment vs Section**

假设一个 ELF 文件编译链接后有这些 Sections：

  * `.init` (初始化代码, 权限 R-X)
  * `.text` (主要代码, 权限 R-X)
  * `.rodata` (只读数据, 权限 R--)
  * `.data` (已初始化数据, 权限 RW-)
  * `.bss` (未初始化数据, 权限 RW-)

如果按 Section 一个个映射，并且每个都要页对齐，可能会浪费很多小块内存。加载器更倾向于按 Segment 加载：

  * **Segment 0 (代码段)**：把 `.init` 和 `.text` 这两个 R-X (只读可执行) 的 Section “打包”成一个 Segment。加载时，作为一个整体映射到内存，并赋予 R-X 权限。
  * **Segment 1 (数据段)**：把 `.rodata`, `.data`, `.bss` 这三个 RW- 或 R-- (可读、可写或只读) 的 Section “打包”成另一个 Segment。加载时，作为一个整体映射，赋予 RW- 权限（因为包含可写部分）。`.bss` 部分在映射时，内存大小 (`p_memsz`) 会比文件大小 (`p_filesz`) 大，多出来的部分会被清零。

这样，原来可能需要映射 5 次（并且可能有 5 次页对齐造成的浪费），现在只需要映射 2 次，更高效，页内碎片也可能更少。你用 `readelf -l <可执行文件>` 看到的就是这些 Segment (类型为 `LOAD`) 的信息。

**例子 4：开张准备 —— 栈的初始化**

当你运行 `./my_program arg1 arg2` 时，在 `main` 函数还没开始执行前，操作系统已经在栈顶帮你准备好了这些东西（简化示意）：

```
(高地址)
...
"SHELL=/bin/bash" <-- 环境变量字符串指针 envp[1] 指向这里
"HOME=/home/user" <-- 环境变量字符串指针 envp[0] 指向这里
NULL              <-- 环境变量列表结束标记
argv[2] ("arg2") 的地址
argv[1] ("arg1") 的地址
argv[0] ("./my_program") 的地址
NULL              <-- 参数列表结束标记 (argv[argc] == NULL)
3                 <-- 参数个数 argc
(栈顶 ESP 指向这里)
(低地址)
```

运行库的入口代码会解析这些信息，然后把 `argc` 和 `argv` 传给你的 `main` 函数。

**例子 5：谁先上场？—— Linux ELF 加载与动态链接器**

在 Linux 下运行一个动态链接的程序，比如 `ls`：

```bash
ldd /bin/ls
```

你会看到类似输出：

```
        linux-vdso.so.1 =>  (0x...)  <-- 特殊的内核 DSO
        libselinux.so.1 => /lib/x86_64-linux-gnu/libselinux.so.1 (0x...)
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x...) <-- C 库！
        libpcre.so.3 => /lib/x86_64-linux-gnu/libpcre.so.3 (0x...)
        libdl.so.2 => /lib/x86_64-linux-gnu/libdl.so.2 (0x...)
        /lib64/ld-linux-x86-64.so.2 (0x...) <-- 动态链接器！
        libpthread.so.0 => /lib/x86_64-linux-gnu/libpthread.so.0 (0x...)
```

  * **依赖关系**：`ls` 这个程序依赖 `libc.so.6` 等好几个共享库。
  * **动态链接器**：注意 `/lib64/ld-linux-x86-64.so.2` 这个家伙！它就是动态链接器。
  * **启动顺序**：内核加载 `ls` 时，发现它需要动态链接器（通过 `.interp` 段知道），于是内核**先加载动态链接器**，然后把控制权交给**动态链接器**。动态链接器再负责去加载 `libc.so.6` 等所有 `ls` 需要的库，进行符号查找和重定位，最后才把控制权交给 `ls` 自己的入口点。

**例子 6：“搬家”的烦恼 —— Windows PE Rebasing**

想象一下 Windows 下的情景：

1.  你的程序 `MyApp.exe` 需要加载 `A.dll` 和 `B.dll`。
2.  `A.dll` 的“期望”加载地址 (ImageBase) 是 `0x10000000`。
3.  `B.dll` 的“期望”加载地址也是 `0x10000000`。
4.  程序启动，加载器先把 `A.dll` 加载到了 `0x10000000`。
5.  接着要加载 `B.dll`，发现期望地址 `0x10000000` 被占了！
6.  加载器只好找个空地儿，比如把 `B.dll` 加载到了 `0x20000000`。
7.  **问题来了**：`B.dll` 内部的代码可能有很多地方写死了基于 `0x10000000` 的绝对地址引用，比如 `call 0x10005000` 或者 `mov eax, [0x10008000]`。现在 `B.dll` 的实际基地址是 `0x20000000`，这些指令显然都不对了！
8.  **Rebasing 出手**：加载器检测到这种情况，就会启动 **Rebasing** 过程。它会查找 `B.dll` 里的重定位信息（`.reloc` 段），找到所有需要修正的绝对地址引用，然后给它们统一加上一个差值（实际加载地址 - 期望基地址，这里是 `0x20000000 - 0x10000000 = 0x10000000`）。于是 `call 0x10005000` 就被**动态修改**成了 `call 0x20005000`，`mov eax, [0x10008000]` 就变成了 `mov eax, [0x20008000]`。
9.  这样，即使 `B.dll` 被“搬家”了，它内部的地址引用也能被正确修正，程序得以正常运行。缺点是这个修正过程需要时间，而且修正后的代码段不能在多个进程间共享了（因为每个进程可能把它 rebase 到不同地址）。
