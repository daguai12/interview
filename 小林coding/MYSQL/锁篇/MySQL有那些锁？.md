# 全局锁

好的，我们来聊聊 MySQL 中的**全局锁 (Global Lock)**。

在 MySQL 中，全局锁是一种**影响整个数据库实例**的锁。它不像表锁或行锁那样只针对特定资源，一旦施加，整个 MySQL 服务都会受到影响。

### 1\. 🔐 核心命令：FTWRL

实现全局锁最典型的命令是：

```sql
FLUSH TABLES WITH READ LOCK;
```

这条命令通常被简称为 **FTWRL**。

-----

### 2\. 🚦 执行效果

当你执行 `FTWRL` 时，MySQL 会做两件事：

1.  **Flush Tables (刷新表)：** 将所有表（包括数据和索引）从内存(Buffer Pool)中刷回到磁盘，并关闭所有正在使用的表。
2.  **WITH READ LOCK (施加全局读锁)：**
      * **阻塞所有写入操作**：整个数据库实例进入**只读状态**。
      * 任何 `INSERT`, `UPDATE`, `DELETE` 语句都会被阻塞。
      * 任何 `CREATE`, `ALTER`, `DROP` 等 DDL 语句也会被阻塞。
      * **允许读取操作**：`SELECT` 语句可以正常执行。

-----

### 3\. 🎯 主要用途：逻辑备份

全局锁最主要（也几乎是唯一）的合理用途是：**进行全库逻辑备份**。

最常见的工具就是 `mysqldump`。

**为什么备份需要全局锁？**
想象一下，你正在备份一个庞大的数据库。你先备份了 `users` 表，然后去备份 `orders` 表。

如果在你备份 `users` 之后、备份 `orders` 之前，有一个用户下了新订单。这个操作会：

1.  在 `orders` 表里插入一条新订单。
2.  在 `users` 表里更新该用户的“最后下单时间”。

这时，你的备份就会出现**数据不一致**：

  * 你的 `orders` 表备份里**没有**这条新订单。
  * 但你的 `users` 表备份里**却包含**了“最后下单时间”的更新。

这个备份恢复回去之后，数据就是错乱的。

使用 `FLUSH TABLES WITH READ LOCK` 可以保证，在你开始备份的那一刻，整个数据库被“冻结”在了一个一致的状态点，所有表都不会再有任何变化，此时的备份才是安全可靠的。

-----

### 4\. ⚠️ 巨大的风险

全局锁是一个**非常重**的操作，它对线上业务的**杀伤力极大**：

  * **业务停摆**：一旦加锁，所有写入请求都会被挂起 (hang 住)。如果你的业务是 7x24 小时提供服务的，这意味着在备份期间，你的网站或 APP 将无法处理下单、注册、修改资料等一切写入操作。
  * **连接堆积**：大量的写入请求被阻塞，会迅速占满 MySQL 的最大连接数，导致新的连接（包括读连接）也无法建立。
  * **主从延迟**：如果你在主库上执行 FTWRL，它会导致主从同步中断（因为主库无法写入 binlog），造成严重的主从延迟。

-----

### 5\. 🔑 如何释放锁

一旦施加了全局锁，有两种方式可以释放它：

1.  **显式释放**：
    ```sql
    UNLOCK TABLES;
    ```
2.  **自动释放**：
    执行 `FTWRL` 命令的那个**客户端连接断开**时，MySQL 会自动释放这个全局锁。`mysqldump` 就是利用这个机制，它在备份完成后会自己断开连接。

-----

### 6\. 👍 更好的替代方案 (InnoDB)

正因为全局锁的风险太大，对于使用 **InnoDB** 存储引擎（现在是默认引擎）的数据库，我们有更好的备份方式。

还记得我们之前讨论的**快照读 (MVCC)** 吗？InnoDB 可以利用它来实现\*\*“热备份”\*\*（不阻塞写入的备份）。

当 `mysqldump` 使用 `–single-transaction` 参数时，它的工作流程是：

1.  **开启一个事务**：执行 `START TRANSACTION WITH CONSISTENT SNAPSHOT;`
2.  **创建快照**：基于 MVCC，在这一刻创建了一个全局的“快照”。
3.  **执行备份**：`mysqldump` 会在这个事务里，用普通的 `SELECT` 语句（快照读）去读取所有表的数据。
4.  **业务继续**：在整个备份期间，其他的事务可以**正常地进行 `INSERT`, `UPDATE`, `DELETE`**。因为它们的操作对 `mysqldump` 所在的那个“快照”是不可见的。

**结论：**

  * 如果你的数据库**全部**是 InnoDB 表，进行逻辑备份时**强烈推荐**使用 `mysqldump --single-transaction`。
  * 只有当你的数据库中还混杂着 MyISAM 这样的**非事务性引擎**时，你才**不得不**使用 `FLUSH TABLES WITH READ LOCK` 这种古老且粗暴的方式来保证数据一致性。

你对 `–single-transaction` 的工作原理（一致性快照）感兴趣吗？

# 表级锁
好的，我们已经聊过了全局锁，现在来谈谈粒度小一点的**表级锁 (Table-Level Lock)**。

顾名思义，表级锁是直接锁定**一整张表**。它是 MySQL 中最基本的锁类型之一，开销最小，但并发性也最差。

-----

### 1\. ⚙️ 表锁的两种主要类型

表锁主要分为两种：

  * **表读锁 (Table Read Lock)**：也叫共享锁 (Shared Lock)。
  * **表写锁 (Table Write Lock)**：也叫排他锁 (Exclusive Lock)。

-----

### 2\. 🚦 锁的兼容性规则

这个规则非常直观，帮你理解为什么它的并发性差：

  * **当前会话 A (持有锁)**
  * **其他会话 B (请求锁)**

| 会话 A 持有... | 会话 B 请求... | 是否兼容 (B是否需要等待)？ | 解释 |
| :--- | :--- | :--- | :--- |
| **读锁 (Read)** | **读锁 (Read)** | **兼容 (不等待)** | “读读”可以并行。大家都可以读，谁也不碍事。 |
| **读锁 (Read)** | **写锁 (Write)** | **不兼容 (等待)** | A 正在读，B 必须等待 A 读完才能写。 |
| **写锁 (Write)** | **读锁 (Read)** | **不兼容 (等待)** | A 正在写，B 必须等待 A 写完才能读。 |
| **写锁 (Write)** | **写锁 (Write)** | **不兼容 (等待)** | “写写”互斥。A 正在写，B 必须等待 A 写完才能写。 |

**总结：**

  * 你可以和很多人**一起读**（读读共享）。
  * 但只要有人在**写**，你就**不能读**。
  * 只要有人在**读**，你就**不能写**。
  * 只要有人在**写**，你就**不能写**。
  * **核心：写操作是完全排他的。**

-----

### 3\. ⌨️ SQL 命令

你可以通过 SQL 显式地控制表锁（虽然不推荐在 InnoDB 中常规使用）：

1.  **加锁**：

    ```sql
    -- 给 users 表加读锁，给 orders 表加写锁
    LOCK TABLES users READ, orders WRITE;
    ```

2.  **释放锁**：

    ```sql
    -- 释放当前会话持有的所有表锁
    UNLOCK TABLES;
    ```

    *注意：* 表锁也会在客户端**连接断开**时自动释放。

-----

### 4\. 🚀 谁在使用表锁？

#### A. MyISAM 存储引擎

**表锁是 MyISAM 引擎的默认和主要锁定策略。**

这就是为什么 MyISAM 引擎**读性能**（因为“读读”不互斥）尚可，但**写性能**（并发写入）极差的原因。只要有一个 `UPDATE` 或 `INSERT` 在执行，整张表都会被锁住，其他所有读写操作都必须排队等待。

#### B. InnoDB 存储引擎

InnoDB 默认使用**行级锁 (Row-Level Lock)**，并发性能远高于 MyISAM。

但是，在某些特定情况下，InnoDB 也会使用表锁：

1.  **显式请求**：当你手动执行 `LOCK TABLES ...` 命令时。
2.  **特殊 DDL**：在执行 `ALTER TABLE` 等 DDL 操作时（这会涉及到下面要讲的 MDL 锁）。
3.  **内部机制**：在某些旧版本或特定配置下，自增锁 (Auto-Inc Lock) 可能会是表锁级别（现在已优化）。

-----

### 5\. ⚠️ 必须知道的：元数据锁 (MDL)

这是一种非常特殊且重要的**表级锁**，它在 MySQL 5.5 版本中引入，用于管理**并发的 DDL 操作**（如 `ALTER TABLE`）和 DML 操作（如 `SELECT`, `UPDATE`）。

  * **MDL 不是 MyISAM 的那种表锁**，而是 MySQL Server 层的功能，**InnoDB 和 MyISAM 都会受它影响**。

  * **它的作用**：保护表的**元数据**（即“表结构”）。

      * 当你要对表执行 DML（`SELECT`, `INSERT` 等）时，MySQL 会自动给你加一个**MDL 读锁**（共享）。
      * 当你要对表执行 DDL（`ALTER TABLE`, `DROP TABLE` 等）时，MySQL 会尝试加一个**MDL 写锁**（排他）。

  * **兼容性**：

      * MDL 读锁之间**兼容**（允许多个 DML 并发）。
      * MDL 写锁与 MDL 读锁、MDL 写锁都**不兼容**。

  * **致命的“陷阱”**：

    1.  一个长事务（例如一个执行了 30 分钟的 `SELECT`）持有一个 **MDL 读锁**。
    2.  此时，一个 `ALTER TABLE` 语句（如加字段）请求 **MDL 写锁**，它会被**阻塞**（等待那个长 `SELECT` 结束）。
    3.  **问题来了**：这个被阻塞的 `ALTER TABLE`，会**阻塞它之后的所有新请求**（包括新的 `SELECT`！）。
    4.  *结果：* 整个表的访问都会被"卡住"，新来的 `SELECT` 堆积如山，导致数据库连接耗尽而宕机。

**总结：**
表级锁（特别是 MyISAM 用的那种）是一种**并发度极低**的锁。而 **MDL 锁**则是一种所有引擎都必须注意的表级锁，尤其是在执行 `ALTER TABLE` 操作时，一定要小心长事务。

---

### 1. 🤯 意向锁 (Intention Lock)

首先，**意向锁是一种表级锁**。

这听起来可能有点绕，但请记住：它的作用是为了**协调“表锁”和“行锁”之间的冲突**，它是一种“信号”锁。

**为什么需要意向锁？**
想象一个场景：
1.  事务 A 用了**行锁**，锁住了 `users` 表中的第 10 行。
2.  此时，事务 B 想要给**整张 `users` 表**加一个**表写锁**（例如 `LOCK TABLES users WRITE;`）。
3.  为了给表加锁，事务 B **必须**检查表里**有没有任何一行**被锁住了。
4.  **如果没有意向锁**：事务 B 必须去**遍历** `users` 表的**每一行**，检查是否有行锁。如果表很大（比如上亿行），这个检查过程的性能是灾难性的。
5.  **有了意向锁**：事务 A 在锁住第 10 行（行锁）之前，会**先**给 `users` **表**加一个“**意向锁**”。这个表锁（意向锁）非常轻量，它只是一个信号，告诉其他事务：“我正准备（或已经）锁住这张表里的某些行”。

现在，当事务 B 想加表写锁时，它**不需要**遍历每一行，它**只需要**检查这张**表**上有没有“意向锁”：
* 如果发现有“意向锁”，事务 B 就知道表里肯定有行被锁了，于是它就**等待**，不用去遍历。

**意向锁的类型：**

* **意向共享锁 (IS Lock)**：
    * “我（事务）准备给这张表里的某些行加**共享锁 (S 锁)**”。
    * 当你执行 `SELECT ... LOCK IN SHARE MODE;` (行级 S 锁) 时，InnoDB 会先自动加上 IS 锁（表级）。
* **意向排他锁 (IX Lock)**：
    * “我（事务）准备给这张表里的某些行加**排他锁 (X 锁)**”。
    * 当你执行 `SELECT ... FOR UPDATE;`、`UPDATE`、`DELETE` (行级 X 锁) 时，InnoDB 会先自动加上 IX 锁（表级）。

**意向锁的兼容性：**
* **意向锁之间是互相兼容的**。
    * 多个事务可以同时持有 IS 锁（大家都想读某几行）。
    * 多个事务可以同时持有 IX 锁（大家都想修改**不同**的行）。
* **意向锁和“真正的”表锁是互斥的** (这才是它的核心作用)：
    * `表读锁 (S)` 与 `意向排他锁 (IX)` 互斥。
    * `表写锁 (X)` 与 `意向共享锁 (IS)`、`意向排他锁 (IX)` 都互斥。

## AUTO_INC锁

**`AUTO_INC` 锁**，也称为**自增锁 (Auto-Increment Lock)**，是 InnoDB 在处理 `AUTO_INCREMENT`（自增）列时使用的一种**特殊的表级锁**。

---

### 1. 🎯 为什么需要自增锁？

它的目的很简单：当**多个事务同时**往一张包含自增列的表里 `INSERT` 数据时，InnoDB 必须保证分配给自增列的 ID 是**唯一**且**严格递增**的。

想象一下，如果两个事务同时插入，都想获取 ID=101，那就乱套了。`AUTO_INC` 锁就是用来协调这个“取号”过程的，确保同一时间只有一个事务能拿到并更新自增计数器。

---

### 2. 🚦 锁的演进：`innodb_autoinc_lock_mode`

`AUTO_INC` 锁的行为并不是一成不变的，它由 `innodb_autoinc_lock_mode` 这个系统参数控制。这个参数有三种设置 (0, 1, 2)，它们代表了性能和连续性之间的不同取舍。

#### A. 模式 0：传统锁 (Traditional)
* **`innodb_autoinc_lock_mode = 0`**
* **行为**：这是最古老的模式。在这种模式下，**任何** `INSERT` 语句（无论快慢）都会获取一个**表级的 `AUTO-INC` 锁**。
* **锁定时长**：这个锁会一直**持有到 `INSERT` 语句执行结束**（注意：是语句结束，不是事务结束）。
* **缺点**：**并发性极差**。如果一个 `INSERT ... SELECT ...`（批量插入）语句需要执行 1 分钟，那么在这 1 分钟内，其他所有事务的 `INSERT` 语句都会被阻塞。

#### B. 模式 1：连续锁 (Consecutive)
* **`innodb_autoinc_lock_mode = 1`** (这是 MySQL 8.0 之前的**默认值**)
* **行为**：这是一个“智能”模式，它会区分不同类型的 `INSERT`：
    * **1. “简单插入” (Simple Inserts)**：
        * 指的是插入前就能**确定要插入多少行**的 `INSERT` 语句（例如 `INSERT VALUES (...)`, `INSERT VALUES (...), (...)`）。
        * **锁机制**：它**不再**使用表级 `AUTO_INC` 锁，而是改用一个**轻量级的互斥锁 (mutex)**。它在内存中分配完需要的 ID 后，**立即释放**这个 mutex，根本不需要等到语句执行结束。
    * **2. “批量插入” (Bulk Inserts)**：
        * 指的是插入前**无法确定具体行数**的 `INSERT`（例如 `INSERT ... SELECT ...`, `LOAD DATA ...`, `REPLACE ... SELECT ...`）。
        * **锁机制**：它**仍然**使用传统的**表级 `AUTO_INC` 锁**，并持有到语句结束。
* **优点**：极大提升了“简单插入”的并发性能。
* **缺点**：当“批量插入”执行时，依然会阻塞所有的“简单插入”。

#### C. 模式 2：交错锁 (Interleaved)
* **`innodb_autoinc_lock_mode = 2`** (这是 MySQL 8.0 及之后的**默认值**)
* **行为**：这是**并发性能最高**的模式。
* **锁机制**：**所有类型**的 `INSERT` 语句（无论是简单还是批量）都**不再**使用表级 `AUTO_INC` 锁，**全部**改用轻量级的 **mutex**。
* **工作方式**：不同的 `INSERT` 语句可以“交错”执行。事务 A 的 `INSERT ... SELECT` 可能刚申请了一批 ID (如 100-150)，事务 B 的 `INSERT VALUES` 就可以立刻进来申请 ID (如 151)，事务 A 再继续申请下一批 (如 152-200)。
* **优点**：**并发性最好**。`INSERT ... SELECT` 不会再阻塞 `INSERT VALUES`。
* **缺点 (代价)**：
    1.  **ID 可能不连续 (Gaps)**：如果一个事务回滚了，它申请的 ID 就会被“浪费”掉，导致 ID 出现“空洞”。（其实模式 1 也会有空洞）。
    2.  **主从复制问题**：这种“交错”分配 ID 的方式，在**基于语句的复制 (SBR)** 模式下会导致主从数据库的自增 ID 不一致。因此，**如果使用 `mode = 2`，你的 binlog 格式必须设置为 `row` (Row-Based Replication)**。

---

### 总结对比

| 模式     | `innodb_autoinc_lock_mode` | 锁机制 (批量插入)               | 并发性能      | ID 连续性  | 复制要求        |
| :----- | :------------------------- | :----------------------- | :-------- | :------ | :---------- |
| **传统** | 0                          | 表级 `AUTO-INC` 锁 (锁到语句结束) | 极差        | 最好      | 无           |
| **连续** | 1                          | 表级 `AUTO-INC` 锁 (锁到语句结束) | 中 (简单插入好) | 较好      | 无           |
| **交错** | 2 (8.0+ 默认)                | 轻量级 Mutex (立即释放)         | **最好**    | 可能交错/空洞 | **必须用 RBR** |

在现代的 MySQL (8.0+) 中，默认使用 `mode = 2` 并且默认使用 `binlog_format = ROW`，这为我们提供了最佳的 `INSERT` 并发性能。

# 行级锁

好的，我们来详细拆解一下 **InnoDB** 引擎中的**行级锁 (Row-Level Lock)**。

这是 InnoDB 实现高并发事务处理的基石。与 MyISAM 锁定整张表不同，InnoDB 能精确地只锁定需要修改的行，允许其他事务同时读写同一张表中的**不同行**。

-----

### 核心要点：行锁是锁在“索引”上的

这是一个最关键、也最容易被误解的概念：

> InnoDB 的行锁，**并不是**直接锁在你的“数据行”（聚簇索引的叶子节点）上，而是**锁在“索引记录” (Index Record) 上的**。

这意味着：

1.  **查询必须命中索引**：如果你的一条 `UPDATE` 语句 `WHERE` 条件**没有**使用任何索引，InnoDB 别无选择，只能**退化为表锁**（或者扫描全表，锁住每一行，效率极低）。
2.  **锁定的精细度**：你使用的索引越精确（如主键 `id=1`），锁的范围就越小。你使用的索引越模糊（如非唯一索引 `age=30`），锁的范围就越大。

-----

### InnoDB 行锁的三种类型

在 MySQL 默认的 **Repeatable Read (RR)** 隔离级别下，为了解决“幻读”问题，InnoDB 引入了三种行锁（或者说，三种锁定了索引记录的算法）：

#### 1\. 记录锁 (Record Lock)

  * **是什么**：这是最简单的行锁，它**只锁定单个索引记录**。
  * **触发条件**：当你的 `WHERE` 子句是**等值查询**，并且命中了**唯一索引**（主键 `PRIMARY KEY` 或 `UNIQUE` 键）时，InnoDB 会对这一条索引记录加 Record Lock。
  * **SQL 示例**：
    ```sql
    -- 假设 id 是主键
    UPDATE users SET name = 'Tom' WHERE id = 10;

    -- 假设 username 是唯一索引
    SELECT * FROM users WHERE username = 'admin' FOR UPDATE;
    ```
  * **效果**：只锁住 `id=10` 这一行，或 `username='admin'` 这一行。其他事务修改 `id=11` 或 `username='guest'` 完全不受影响。

#### 2\. 间隙锁 (Gap Lock)

  * **是什么**：它**只锁“间隙”**，不锁任何实际存在的记录。它锁定的是**索引记录之间的“空隙”**，或者第一个记录前的“空隙”，或最后一个记录后的“空隙”。
  * **核心目的**：**防止幻读**。Gap Lock 的唯一作用就是阻止其他事务在这个“间隙”中执行 `INSERT` 操作。
  * **触发条件**：当你执行**范围查询**（如 `>`、`<`、`BETWEEN`）或者查询一个**不存在的记录**时，InnoDB 就会在相应的“间隙”上加 Gap Lock。
  * **SQL 示例**：
    ```sql
    -- 假设表中有 id 为 10 和 20 的记录，但没有 15
    SELECT * FROM users WHERE id = 15 FOR UPDATE;

    -- 效果：InnoDB 会在 (10, 20) 这个间隙上加 Gap Lock。
    -- 结果：其他事务无法 INSERT id 为 11, 12 ... 19 的新数据。

    -- 另一个例子
    SELECT * FROM users WHERE age > 100 FOR UPDATE;

    -- 效果：如果 age 索引上最大值是 80，
    -- InnoDB 会在 (80, +∞) 这个间隙上加 Gap Lock。
    -- 结果：其他事务无法 INSERT age > 100 的新数据。
    ```
  * **注意**：Gap Lock 之间是**兼容**的。两个事务可以**同时**在 `(10, 20)` 这个间隙上持有 Gap Lock，但它们俩谁也别想往里 `INSERT` 数据。

#### 3\. 临键锁 (Next-Key Lock)

  * **是什么**：这是 InnoDB 在 RR 级别下的**默认行锁算法**。
  * **Next-Key Lock = 记录锁 (Record Lock) + 间隙锁 (Gap Lock)**
  * **锁定范围**：它既锁住了**索引记录本身**，也锁住了该**记录之前的那个“间隙”**。这是一个“左开右闭” `(previous_key, current_key]` 的区间。
  * **触发条件**：当你的查询命中了**非唯一索引**时，或者使用了**范围查询**时。
  * **SQL 示例**：
    ```sql
    -- 假设 'age' 是一个非唯一索引，表中有 10, 20, 30 三条记录
    UPDATE users SET name = 'Test' WHERE age = 20;
    ```
  * **效果**：
    InnoDB 不会只锁住 `age=20` 的那（几）行。它会使用 Next-Key Lock，锁住 `(10, 20]` 这个区间。
      * `Record Lock`：锁住了所有 `age=20` 的**记录**。
      * `Gap Lock`：锁住了 `(10, 20)` 这个**间隙**。
  * **结果**：其他事务不仅**不能**修改 `age=20` 的行，也**不能** `INSERT` `age` 为 11 到 19 的新数据。

**为什么需要 Next-Key Lock？**

  * 如果只用 Record Lock，事务 A `UPDATE age=20`。事务 B 仍然可以 `INSERT age=15`。事务 A 再次查询 `age >= 20` 时就会发现多了数据（幻读）。
  * Next-Key Lock 通过锁住间隙，彻底杜绝了其他事务 `INSERT` 的可能性，从而解决了幻读问题。

-----

### 特例：插入意向锁 (Insert Intention Lock)

这是一种特殊的**间隙锁 (Gap Lock)**，它是在 `INSERT` 操作之前设置的。

  * 当一个事务尝试 `INSERT` 一条新记录时，它必须检查目标“间隙”是否被 Gap Lock 或 Next-Key Lock 锁住。
  * 如果没有被锁，`INSERT` 事务会为自己设置一个**插入意向锁**，表示“我准备插进来了”。
  * 插入意向锁之间**不互斥**。多个事务可以同时在同一个间隙中等待（只要它们插入的键值不冲突），但它们都必须等待那个持有“间隙锁”的事务释放锁。

-----

### 隔离级别的影响

最后，你需要知道，上面讨论的**Gap Lock** 和 **Next-Key Lock** 主要是为了实现 **Repeatable Read (RR)** 隔离级别。

如果你将 MySQL 的隔离级别设置为 **Read Committed (RC)**：

  * InnoDB 会**禁用** Gap Lock（绝大多数情况下）。
  * 行锁会**退化**为纯粹的 **Record Lock**。
  * **好处**：锁的粒度更小，并发性能**更高**（因为 `UPDATE` 不会锁住间隙了）。
  * **代价**：**无法**阻止幻读。

### 总结

| 锁类型 | 锁定目标 | 主要目的 | RR 级别 | RC 级别 |
| :--- | :--- | :--- | :--- | :--- |
| **Record Lock** | 单个索引记录 | 锁定数据行 | ✔️ | ✔️ (主要) |
| **Gap Lock** | 索引间的“间隙” | 防止幻读 (Insert) | ✔️ | ❌ (基本禁用) |
| **Next-Key Lock** | 记录 + 记录前的间隙 | 锁定数据 + 防止幻读 | ✔️ (默认) | ❌ |
