这是一个非常核心的 MySQL 优化问题！"索引失效" 是面试和实际工作中排查性能问题的关键。

“索引失效”并不是指索引“坏了”，而是指 **MySQL 优化器**在执行 SQL 时，**决定“不使用”这个索引**，而是退回到“全表扫描” (Full Table Scan)，导致查询变慢。

以下是导致索引失效的最常见的几种情况：

-----

### 1\. 违反“最左前缀法则” (针对联合索引)

这是最容易犯的错误。如果您有一个联合索引 `idx_a_b_c (col_a, col_b, col_c)`，查询必须从最左边的 `col_a` 开始，并且**不能跳过**中间的列。

  * **✅ 生效：** `WHERE col_a = '...'`
  * **✅ 生效：** `WHERE col_a = '...' AND col_b = '...'`
  * **❌ 失效：** `WHERE col_b = '...'` (跳过了 `col_a`)
  * **❌ 失效：** `WHERE col_a = '...' AND col_c = '...'` (`col_c` 部分失效，因为跳过了 `col_b`)

### 2\. 在索引列上“动手术” (函数、计算、转换)

这是最致命的失效原因。索引保存的是“原始值”，一旦您在 `WHERE` 子句中对索引列进行了任何操作，索引就无法匹配了。

  * **❌ 失效 (使用函数)：**

    ```sql
    WHERE DATE_FORMAT(create_time, '%Y-%m') = '2025-11';
    ```

      * **✅ 拯救：** 应该把函数用在“常量”上：`WHERE create_time >= '2025-11-01' AND create_time < '2025-12-01';`

  * **❌ 失效 (隐式类型转换)：** (假设 `phone` 列是 `VARCHAR` 字符串类型)

    ```sql
    WHERE phone = 13800001111; -- 提供了数字，MySQL会强制转换列
    ```

      * **✅ 拯救：** 保持类型一致：`WHERE phone = '13800001111';`

  * **❌ 失效 (进行计算)：**

    ```sql
    WHERE age - 1 = 20;
    ```

      * **✅ 拯救：** 把计算移到右边：`WHERE age = 21;`

### 3\. `LIKE` 查询以通配符 `%` 开头

B+ 树索引是从左到右排序的。如果您连开头是什么都不知道，索引就无法帮您定位。

  * **✅ 生效 (前缀匹配)：**
    ```sql
    WHERE name LIKE '张%';
    ```
  * **❌ 失效 (前导通配符)：**
    ```sql
    WHERE name LIKE '%三';
    ```
  * **❌ 失效 (中间通配符)：**
    ```sql
    WHERE name LIKE '%三%';
    ```

### 4\. `OR` 条件中包含未索引的列

如果 `OR` 连接的条件中，**只要有一个**列没有索引，MySQL 优化器就可能放弃**所有**索引，转而使用全表扫描。

  * **❌ 失效：** (假设 `email` 列没有索引)
    ```sql
    WHERE name = '张三' OR email = 'zhangsan@email.com';
    ```
      * (优化器会想：反正查 `email` 都要全表扫描了，还不如一次性全表扫描把 `name` 也顺便找了。)

### 5\. 负向查询 (`!=`, `<>`, `NOT IN`, `NOT EXISTS`)

负向查询通常意味着你需要匹配的数据**非常多**。MySQL 优化器会“估算成本”，认为还不如直接全表扫描。

  * **❌ 可能失效：**
    ```sql
    WHERE status != 1;
    ```
    ```sql
    WHERE id NOT IN (1, 2, 3);
    ```

### 6\. 优化器认为“全表扫描”更快 (成本估算)

这是索引失效的**根本原因**。MySQL 采用的是**成本估算优化器 (CBO)**。

  * **场景：** 比如您在“性别”(`gender`)列上有索引，您查询 `WHERE gender = '男'`。
  * **优化器估算：**
    1.  **方案 A (用索引)：** 先查 `gender` 索引，发现 `gender = '男'` 的数据占了全表的 50%。然后还要“回表” 50% 的数据行。**成本很高**。
    2.  **方案 B (全表扫描)：** 直接从头到尾读一遍表，把 `gender = '男'` 的数据全拿走。**成本更低**。
  * **结论：** 优化器**主动放弃**索引，选择方案 B (全表扫描)。这在查询“低区分度”的列（如性别、状态）时非常常见。

-----

### 💡 终极武器：`EXPLAIN`

如何知道您的索引是否失效了？**不要猜！**

在您的 `SELECT` 语句前加上 `EXPLAIN` 关键字，然后查看 `type` 列：

```sql
EXPLAIN SELECT * FROM users WHERE name LIKE '%三';
```

  * **`type = ALL`**： 意味着**全表扫描**，索引**已失效**！
  * **`type = range` / `ref` / `eq_ref` / `const`**： 意味着**成功使用**了索引。
