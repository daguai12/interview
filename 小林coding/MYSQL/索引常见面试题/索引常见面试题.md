# 什么时候适用索引?

这是一个非常非常重要的问题！理解何时使用索引，是从 "会写 SQL" 进阶到 "会优化 SQL" 的关键一步。

简单来说，**索引就像一本书的“目录”**。

  * **没有索引 (全表扫描)：** 当你找一个知识点时，你必须**从第一页翻到最后一页**，直到找到它。如果书很厚（数据表很大），这会非常慢。
  * **有了索引 (索引查找)：** 你先去查“目录”（索引），目录告诉你这个知识点在第 205 页（数据在磁盘上的位置），你**直接翻到第 205 页**。这会非常快。

索引的核心价值是：**极大提升查询 (`SELECT`) 速度**，以**牺牲一点写入 (`INSERT`/`UPDATE`/`DELETE`) 速度和存储空间**为代价。

-----

### 🚀 黄金法则：何时适用索引

当你的表“**读多写少**”（查询远多于增删改）时，索引的效果最好。

以下是几个**必须**考虑使用索引的具体场景：

#### 1\. `WHERE` 子句中频繁用到的“条件列”

这是**最首要、最常见**的场景。如果你经常根据某个列来“筛选”数据，它就应该被索引。

  * **场景：** 你经常需要通过“用户名”来查找用户。
  * **SQL 示例：**
    ```sql
    SELECT * FROM users WHERE username = 'zhangsan';
    ```
  * **策略：** 必须在 `username` 列上创建索引。否则，MySQL 会扫描 `users` 表的**每一行**来寻找 'zhangsan'。

#### 2\. `JOIN` 子句中的“连接键”

在连表查询时，用于 `ON` 后面的“连接键”（通常是外键 `user_id` 和主键 `id`）**必须**被索引。

  * **场景：** 查询用户及其所有订单。
  * **SQL 示例：**
    ```sql
    SELECT u.name, o.product
    FROM users AS u
    JOIN orders AS o ON u.user_id = o.user_id;
    ```
  * **策略：** `users.user_id`（通常是主键，默认有索引）和 `orders.user_id`（外键）都应该被索引。如果没有索引，MySQL 在进行连接时，可能需要对一张表进行多次“全表扫描”，性能会随着数据量增长而急剧下降。

#### 3\. `ORDER BY` 子句中的“排序列”

如果你需要对查询结果进行排序，索引可以帮助 MySQL **避免昂贵的“文件内排序” (Filesort)**。

  * **场景：** 经常需要按“创建时间”倒序查看最新的文章。
  * **SQL 示例：**
    ```sql
    SELECT * FROM articles ORDER BY create_time DESC;
    ```
  * **策略：** 在 `create_time` 列上创建索引。MySQL 可以直接按照索引中已经排好序的顺序去读取数据，而不需要先把所有数据读入内存，再进行一次“排序”操作。

#### 4\. `GROUP BY` 子句中的“分组合”

`GROUP BY` 的优化原理与 `ORDER BY` 类似。索引可以帮助数据库快速地找到所有相同分组的数据。

  * **场景：** 统计每个部门的员工数量。
  * **SQL 示例：**
    ```sql
    SELECT department, COUNT(*)
    FROM employees
    GROUP BY department;
    ```
  * **策略：** 在 `department` 列上创建索引，有助于 `GROUP BY` 的性能。

#### 5\. 列的“高区分度”（高基数）

“区分度”（Cardinality）指的是一个列中不重复值的多少。

  * **高区分度（适合索引）：** 像 `user_id`、`username`、`email` 这样的列，每个值几乎都是唯一的。索引效率**极高**。
  * **低区分度（不适合索引）：** 像 `gender`（性别，只有 '男', '女', '未知'）、`status`（状态，只有 '已支付', '未支付'）这样的列。
      * 索引效率**极低**。因为你查 `gender = '男'`，可能一下就命中了 50% 的数据，MySQL 发现还不如直接全表扫描来得快，就会**放弃使用索引**。

-----

### 🚫 黄金法则：何时不适用（或慎用）

索引不是免费的，它有成本：

1.  **空间成本：** 索引本身就是一个数据结构（B+ 树），需要额外占用磁盘空间。
2.  **写入成本（最主要的成本）：**
      * `INSERT`：插入新数据时，不仅要写入数据表，还必须**更新索引**（在 B+ 树中添加新节点）。
      * `UPDATE`：如果更新了被索引的列（比如修改了 `username`），索引也必须**更新**。
      * `DELETE`：删除数据时，索引也必须**标记为删除**。

#### 1\. “写多读少”的表

  * **场景：** 比如“日志表” (log)，它每秒钟有几千次 `INSERT` 操作，但一天可能只被 `SELECT` 查询几次（用于分析）。
  * **策略：** 这种表**不应该**加索引（或只加最必要的索引），因为索引带来的“写入成本”远大于它带来的“查询收益”。

#### 2\. “小表”

  * **场景：** 一张“国家配置表”，总共就 200 多行。
  * **策略：** **完全不需要**索引。因为数据量太小，MySQL "全表扫描" 的速度快到可以忽略不计（甚至比读取索引的开销还小）。

#### 3\. “低区分度”的列

  * **场景：** `gender` (性别) 列。
  * **策略：** 如上所述，不适合单独创建索引。

### 总结

| 场景                | 推荐操作     |
| :---------------- | :------- |
| `WHERE` 条件列       | **强烈推荐** |
| `JOIN` 连接键        | **强烈推荐** |
| `ORDER BY` 排序列    | **推荐**   |
| `GROUP BY` 分组列    | 推荐       |
| 表非常小 (\< 1000 行)  | **不需要**  |
| 表“写多读少” (如 Log)   | **不要加**  |
| 列的区分度极低 (如性别)<br> | **不要加**  |
|                   |          |
|                   |          |

# 什么时候不需要创建索引？

这是一个非常好的问题！我们刚刚讨论了“何时**要**创建索引”，反过来理解“何时**不要**创建索引”同样重要。

创建索引是有代价的，它会**占用磁盘空间**，并且在 `INSERT`、`UPDATE`、`DELETE`（增、删、改）时**增加 I/O 开销**，因为数据库不仅要修改数据行，还必须同步更新索引（B+ 树）。

**核心原则：如果创建索引带来的“查询收益”小于它带来的“维护成本”，就不应该创建。**

---

### 🚫 黄金法则：何时不需要（或不应该）创建索引

以下是几个最典型的不需要创建索引的场景：

#### 1. “表”太小（The Small Table）

* **场景：** 比如一张“省份配置表”、“部门表”或者“权限角色表”，全表加起来可能只有几十行或几百行数据。
* **原因：** 数据量太小，MySQL "全表扫描"（从头读到尾）的速度快到可以忽略不计。在这种情况下，去查“目录”（索引）再根据目录去找数据，这个过程的开销**甚至可能比直接全表扫描还要慢**。
* **法则：** 通常，几百行到一千行以下的“小表”，没必要额外创建索引（主键索引除外）。

#### 2. “写多读少”的表（The Write-Heavy Table）

* **场景：** 典型的如“日志表 (Logs)”、“用户操作记录表”、“实时指标采集表”。这类表每秒钟可能有成百上千次 `INSERT` 操作，但可能每小时才会被 `SELECT` 查询分析一次。
* **原因：** 索引的主要收益在 `SELECT`。如果 `INSERT` 和 `UPDATE` 的频率远高于 `SELECT`，那么每次写入数据时“维护索引”所带来的性能开销（I/O 消耗），将远远大于索引偶尔带来的查询收益。
* **法则：** 对于写入极其频繁、查询很少的表，应**尽可能少地创建索引**。

#### 3. “区分度”极低的列（The Low-Cardinality Column）

* **场景：** 比如 `gender` (性别) 列（只有 '男', '女', '未知' 3 种值）、`status` (状态) 列（如 '已支付', '未支付', '已取消'）、`is_active` (是否激活) 列（只有 0 和 1）。
* **原因：** 索引的价值在于“快速定位”。如果你在 `gender` 列上建索引，当你查询 `WHERE gender = '男'` 时，索引会告诉你“50% 的数据都符合条件”。MySQL 发现与其使用这个“模糊”的索引，还不如直接“全表扫描”来得快，因此会**放弃使用这个索引**。
* **法则：** 区分度（Cardinality，不重复值的数量）太低的列，不适合单独创建索引。

#### 4. 很少在查询条件中使用的列（The Unused Column）

* **场景：** 比如 `users` 表中的 `description` (个人简介) 列，它只是用来存储和展示的，几乎没有人会用 `WHERE description LIKE '%...%'` 来查询。
* **原因：** 创建索引的唯一目的就是为了优化 `WHERE`、`JOIN`、`ORDER BY`、`GROUP BY`。如果一个列根本不参与这些操作，创建索引就**毫无意义**，纯粹是浪费空间和写入性能。

#### 5. 已经存在“联合索引”的前缀列（The Redundant Index）

* **场景：** 这是一个新手常见的错误。假设你已经创建了一个联合索引：`INDEX idx_a_b (col_a, col_b)`。
* **原因：** 在 MySQL 中，这个联合索引 `(col_a, col_b)` 已经可以被 `WHERE col_a = '...'` 的查询所**复用**（遵循“最左前缀原则”）。
* **法则：** 如果你已经有了 `(A, B)` 联合索引，那么**不需要**再单独为 `(A)` 创建一个索引，这是多余的（Redundant）。（但如果你想单独查询 `B`，`idx_a_b` 索引是无效的）。

### 总结

| 场景 | 原因 |
| :--- | :--- |
| **1. 小表** (几百行) | 全表扫描足够快，索引是多余的开销。 |
| **2. 写多读少** (如日志表) | 索引带来的“写入维护成本”远大于“查询收益”。 |
| **3. 低区分度** (如性别) | 索引筛选不出少量数据，MySQL 会放弃使用它。 |
| **4. 很少被查询** (如备注) | 索引的优化目的不存在，纯属浪费。 |
| **5. 冗余索引** (已有 (A,B)，又建 A) | 已有的联合索引可以覆盖该查询，浪费空间。 |

# 什么时候索引会失效？

这是一个**非常、非常核心**的 MySQL 优化问题！

"索引失效" 并不是指索引坏了或消失了，而是指：**你明明在某个列上创建了索引，但在执行 SQL 查询时，MySQL 的“优化器” (Optimizer) 却**`选择不使用`**这个索引，而是退化为“全表扫描” (Full Table Scan)。**

这就像你有一本字典的目录（索引），但你的查询方式让这个目录变得毫无用处，迫使你只能从第一页翻到最后一页。

以下是导致索引失效的最常见的几种情况，以及如何“拯救”它们。

-----

### 1\. 违反“最左前缀法则” (针对联合索引)

这是**最重要**、也**最容易出错**的一种情况。

  * **联合索引 (Combined Index)：** 假设你创建了一个“联合索引”，比如 `INDEX idx_a_b_c (col_a, col_b, col_c)`。
  * **法则：** MySQL 必须**从索引的最左边开始**连续使用，不能跳过中间的列。
  * **类比：** 就像查字典，你必须先按首字母 `a` 查，再按第二个字母 `b` 查。

**示例：`INDEX idx_name_dept (name, department)`**

| SQL 查询                                     | 是否使用索引      | 原因                                                   |
| :----------------------------------------- | :---------- | :--------------------------------------------------- |
| `WHERE name = '张三'`                        | **是**       | 遵循最左前缀。                                              |
| `WHERE name = '张三' AND department = '研发部'` | **是**       | 遵循最左前缀。                                              |
| `WHERE department = '研发部'`                 | **否 (失效！)** | **查询跳过了 `name`**，直接从第二列开始，索引无法定位。                    |
| `WHERE department = '研发部' AND name = '张三'` | **是**       | MySQL 优化器很智能，会自动帮你**调整顺序**为 `name` -\> `department`。 |

### 2\. 在索引列上“动手术” (函数、计算、转换)

这是**最致命**的一种情况。

  * **法则：** 索引保存的是“原始值”。如果你对列进行了任何函数运算、计算或类型转换，索引将无法匹配。
  * **类比：** 目录里存的是“张三”，你却要查 `LEFT('张三', 1) = '张'`，目录帮不了你。

**示例：`idx_create_time (create_time)` (DATE 类型)**

  * **❌ 错误 (失效)：** (在索引列上用了函数)
    ```sql
    WHERE DATE_FORMAT(create_time, '%Y-%m') = '2025-11';
    ```
  * **✅ 正确 (使用索引)：** (把“手术”移到常量一侧)
    ```sql
    WHERE create_time >= '2025-11-01' AND create_time < '2025-12-01';
    ```

**示例：`idx_phone (phone)` (VARCHAR 字符串类型)**

  * **❌ 错误 (失效)：** (隐式类型转换)
    ```sql
    WHERE phone = 13800001111; -- (你提供了数字, 但列是字符串)
    ```
    *MySQL 会在内部把**每一行**的 `phone` 都 `CAST` 为数字再比较，相当于在索引列上用了函数！*
  * **✅ 正确 (使用索引)：**
    ```sql
    WHERE phone = '13800001111'; -- (保持类型一致, 使用引号)
    ```

### 3\. `LIKE` 查询以通配符 `%` 开头

  * **法则：** B+ 树索引是从左到右排序的。如果你连开头是什么都不知道，索引就无法帮你定位。
  * **类比：** 查字典时，你只知道一个词的结尾是 `...ing`，你无法使用目录。

**示例：`idx_name (name)`**

  * **✅ 正确 (使用索引)：** (前缀匹配)
    ```sql
    WHERE name LIKE '张%';
    ```
  * **❌ 错误 (失效)：** (前导通配符)
    ```sql
    WHERE name LIKE '%三';
    ```
  * **❌ 错误 (失效)：** (中间通配符)
    ```sql
    WHERE name LIKE '%三%';
    ```

### 4\. `OR` 条件中包含未索引的列

  * **法则：** 如果 `OR` 连接的条件中，**只要有一个**列没有索引，MySQL 优化器就可能放弃**所有**索引，转而使用全表扫描。
  * **类比：** 经理让你“去 `idx_a` 找 A，或者去 `(无索引的)b` 找 B”。你发现找 B 反正都要全表扫描，还不如一次性全表扫描把 A 和 B 都找了。

**示例：`idx_name (name)`**

  * **❌ 错误 (失效)：** (`email` 列没有索引)
    ```sql
    WHERE name = '张三' OR email = 'zhangsan@email.com';
    ```
  * **✅ 正确 (使用索引)：** (确保 `OR` 两边的列都有索引)
    ```sql
    WHERE name = '张三' OR department = '研发部'; -- (假设 name 和 department 都有索引)
    ```

### 5\. `!=`、`NOT IN`、`NOT EXISTS` (负向查询)

  * **法则：** 负向查询 (`!=`, `<>`, `NOT IN`) 通常意味着你需要匹配的数据**非常多**。
  * **原因 (见下一条)：** 优化器会“算一笔账”，觉得不划算。

### 6\. 优化器认为“全表扫描”更快 (成本估算)

这是索引失效的**根本原因**。MySQL 使用的是**成本估算优化器 (Cost-Based Optimizer, CBO)**。

  * **场景：** 比如你查询 `WHERE status = 1`，`status` 也有索引。但是表里 90% 的数据 `status` 都是 1。
  * **优化器估算：**
    1.  **方案 A (用索引)：** 先查 `status` 索引 (I/O)，再根据索引结果，逐条回表查询 90% 的数据行 (大量随机 I/O)。**成本很高**。
    2.  **方案 B (全表扫描)：** 直接从头到尾读一遍表，把 `status = 1` 的数据全拿走 (一次顺序 I/O)。**成本更低**。
  * **结论：** 优化器**主动放弃**索引，选择方案 B。

> **何时发生？**
>
>   * 当你使用 `!=`、`NOT IN` 时（因为它们通常会返回大量数据）。
>   * 当你查询“低区分度”的列时（如“性别”、“状态”）。
>   * 当你使用 `IS NULL` / `IS NOT NULL`，且 `NULL` 值占比很高/很低时。

-----

### 总结：如何判断索引是否失效？

**“实践是检验真理的唯一标准。”**

在你**所有**的 `SELECT` 语句前，加上 `EXPLAIN` 关键字，然后查看 `type` 列：

```sql
EXPLAIN SELECT * FROM users WHERE name LIKE '%三';
```

  * **`type = ALL`**： 意味着**全表扫描**，索引**已失效**！
  * **`type = index`**： 意味着全索引扫描（比 `ALL` 稍好，但也不理想）。
  * **`type = range` / `ref` / `eq_ref` / `const`**： 意味着**成功使用**了索引。

这是面试和实际工作中排查性能问题的**必备神技**。


# 有什么优化索引的方法?

问得非常好！我们前面讨论了“何时用”、“何时不用”和“何时失效”，现在我们来谈\*\*“如何让它变得更强”\*\*——这就是索引优化。

优化索引的核心思想有两个：

1.  **“精准打击”：** 让一个索引尽可能**精准地**覆盖你的查询，避免“浪费”。
2.  **“避免回表”：** 尽可能让数据库**只看“目录”（索引）就能拿到所有数据，而不要**再回去翻“正文”（数据表）。

-----

### 🚀 索引优化的四大黄金法则

#### 1\. 法则一：精准设计“联合索引” (Composite Indexes)

**“联合索引”**（也叫复合索引）是在**多个列**上建立一个索引。这是**最常用、最重要**的优化手段。

  * **为什么？**

      * *反例：* 你有两个查询：`WHERE name = 'A'` 和 `WHERE department = 'B'`。你创建了两个单列索引：`idx_name(name)` 和 `idx_dept(department)`。
      * *问题：* 如果你的查询是 `WHERE name = 'A' AND department = 'B'`，MySQL 通常**只能选择其中一个索引**（比如 `idx_name`），然后再在查到的结果里（可能是几千行）去慢慢过滤 `department = 'B'`，效率不高。

  * **优化方法：创建联合索引**
    创建一个 `INDEX idx_name_dept (name, department)`。
    这个索引同时包含了 `name` 和 `department`，查询 `WHERE name = 'A' AND department = 'B'` 时，可以完美命中，速度极快。

  * **设计的“黄金顺序”：**
    设计联合索引时，列的顺序**至关重要**。你需要遵循“最左前缀法则”，但顺序该如何定？

    1.  **选择性（区分度）高的列放前面：**
          * `username`（几百万个都不一样）和 `status`（只有 3, 4 个值）。
          * **✅ 优选：** `(username, status)`
          * **❌ 糟糕：** `(status, username)`。因为查 `status` 筛选不出什么数据。
    2.  **等值查询 (`=`) 的列放前面，范围查询 (`>`, `<`, `LIKE`) 的列放后面：**
          * *查询：* `WHERE name = '张三' AND age > 20;`
          * **✅ 优选：** `(name, age)`
          * **❌ 糟糕：** `(age, name)`。如果先按 `age > 20` 查，B+ 树无法精确定位 `name`。

#### 2\. 法则二：使用“覆盖索引” (Covering Index)

**“覆盖索引”是索引优化的“圣杯”**。它能带来极大的性能提升。

  * **什么是“回表” (Back-to-Table)？**

      * *场景：* 你在 `name` 列上有个 `idx_name(name)` 索引。
      * *查询：* `SELECT name, email FROM users WHERE name = '张三';`
      * *执行过程 (慢)：*
        1.  MySQL 查找 `idx_name` 索引，定位到“张三”。（很快）
        2.  在 `idx_name` 索引上，它只找到了“张三”的**主键 ID** (比如 `101`)。
        3.  但是你需要 `email` 列，索引上没有。
        4.  MySQL 必须拿着主键 `101`，**再**去“主键索引”（数据表本身）中找到第 101 行，取出 `email`。
      * 这个“**再回去查一次**”的动作，就叫\*\*“回表”\*\*。

  * **优化方法：使用“覆盖索引”避免回表**

      * *修改索引：* 创建一个 `INDEX idx_name_email (name, email)`。
      * *新查询过程 (飞快)：*
        1.  MySQL 查找 `idx_name_email` 索引。
        2.  它在索引上直接找到了 `name = '张三'`，并且**发现 `email` 字段也在这个索引上**！
        3.  它**直接从索引中返回** `name` 和 `email`，**不需要再回数据表**。

  * **如何判断：**
    使用 `EXPLAIN` 分析 SQL，如果 `Extra` 列显示 **`Using index`**，恭喜你，你成功使用了“覆盖索引”！

#### 3\. 法则三：规避“索引失效” (Re-write SQL)

这是我们上一节讨论过的“索引失效”的反向操作。**你不需要修改索引，你只需要修改你的 SQL 写法。**

  * **❌ 错误 (在索引列上“动手术”)：**

    ```sql
    WHERE DATE_FORMAT(create_time, '%Y-%m') = '2025-11';
    ```

  * **✅ 优化 (保持索引列“干净”)：**

    ```sql
    WHERE create_time >= '2025-11-01' AND create_time < '2025-12-01';
    ```

  * **❌ 错误 (隐式类型转换)：** (phone 是字符串)

    ```sql
    WHERE phone = 13800001111;
    ```

  * **✅ 优化 (保持类型一致)：**

    ```sql
    WHERE phone = '13800001111';
    ```

  * **❌ 错误 (前导模糊查询)：**

    ```sql
    WHERE name LIKE '%三';
    ```

  * **✅ 优化 (使用前缀查询)：**

    ```sql
    WHERE name LIKE '张%';
    ```

#### 4\. 法则四：清理“冗余和未使用”的索引 (Maintenance)

索引不是越多越好。**你每多一个索引，你的 `INSERT`、`UPDATE`、`DELETE` 就会慢一分**，因为它要去维护这个索引。

  * **冗余索引 (Redundant)：**
      * 你已经有了 `(name, department)` 联合索引。
      * 你又“好心”地创建了一个 `(name)` 单列索引。
      * 这个 `(name)` 索引就是**完全冗余**的，因为 `(name, department)` 索引已经可以完美覆盖 `WHERE name = '...'` 的查询。**必须删除它**。
  * **未使用索引 (Unused)：**
      * 你创建了一个 `(age)` 索引，但上线 3 个月了，没有一个 SQL 查询使用过它（比如业务调整，不再按年龄查了）。
      * 这个索引纯粹是在**拖慢写入性能**。**必须删除它**。

-----

### 总结：优化的神器 `EXPLAIN`

你该如何知道你的优化是否有效？

**答案是：`EXPLAIN`**。

在你的 `SELECT` 语句前加上 `EXPLAIN`，MySQL 会告诉你它**打算如何执行**这个查询。

```sql
EXPLAIN SELECT name, email FROM users WHERE name = '张三';
```

你需要重点关注几列：

  * **`type`：** 必须避免 `ALL` (全表扫描)。最好是 `ref`、`range`，最好是 `const`。
  * **`key`：** 实际**使用**了哪个索引。
  * **`Extra`：**
      * **`Using index`：** 完美！命中了“覆盖索引”。
      * **`Using where`：** 还需要在索引结果上再过滤。
      * **`Using filesort`：** 糟糕！MySQL 正在进行代价昂贵的“文件排序”，说明你的 `ORDER BY` 没用上索引。

-----

您想不想学习一下如何**详细阅读 `EXPLAIN` 的分析结果**？这是 MySQL 调优的必备技能。


# 补充

您提的这个问题**非常精准**，直指联合索引的核心！您说的没错：

* `age > 20` **会**用到 `(age, name)` 这个联合索引。
* `name = '张三'` 在 `age > 20` **之后**，索引的“定位”功能就失效了。

您对现象的观察是 100% 正确的！而**“为什么这就算糟糕 (Bad)”**，则在于**效率对比**。

我们来深入拆解一下B+ 树索引的工作原理，看看 `(name, age)` 和 `(age, name)` 这两种索引在面对 `WHERE name = '张三' AND age > 20` 这个查询时，到底发生了什么。

---

### 联合索引的“天条”

联合索引 `(col_a, col_b)`，它的B+树在物理上是：
1.  **先严格按照 `col_a` 排序。**
2.  **在 `col_a` 相同的情况下，再按照 `col_b` 排序。**

**核心规则：** 一旦在 `col_a` 上进行了**范围查询**（`>`、`<`、`LIKE %`、`BETWEEN`），`col_b` 的“排序性”就无法被利用了，索引的**定位功能**（Seek）就会**中断**。

---

### 对比两种索引的执行过程

#### 场景 A (优选): `INDEX (name, age)`

* **索引结构：** 先按 `name` 排序，再按 `age` 排序。
    * '李四', 18
    * '李四', 25
    * **'张三', 19** <-- (步骤1: 精确定位到 '张三' 的开头)
    * **'张三', 21** <-- (步骤2: 开始扫描 age)
    * **'张三', 25** <-- (步骤2: 继续扫描 age)
    * '王五', 20

* **执行步骤：**
    1.  **`WHERE name = '张三'` (等值查询)：**
        MySQL 使用索引的 `name` 部分，像二分查找一样**“精确定位” (Seek)** 到 `name = '张三'` 的**第一条**记录（`'张三', 19`）。这是一个极快的 O(logN) 操作。
    2.  **`AND age > 20` (范围查询)：**
        在 `name = '张三'` 这个**很小**的“数据块”中，`age` (19, 21, 25) 也是排好序的。MySQL 沿着这个小块继续**“扫描” (Scan)**，找到所有 `age > 20` 的记录（即 '张三', 21 和 '张三', 25）。

* **效率总结：** `精确定位 (name)` + `小范围扫描 (age)`。效率极高。

---

#### 场景 B (糟糕): `INDEX (age, name)`

* **索引结构：** 先按 `age` 排序，再按 `name` 排序。
    * 18, '李四'
    * 19, '张三'
    * 20, '王五'
    * **21, '张三'** <-- (步骤1: 定位到 age=21)
    * **25, '李四'** <-- (步骤1: 扫描...)
    * **... (假设这里还有 100 万条 age > 20 的记录) ...**
    * **50, '张三'** <-- (步骤1: 扫描...)

* **执行步骤：**
    1.  **`WHERE age > 20` (范围查询)：**
        MySQL 使用索引的 `age` 部分，定位到 `age = 21` 的记录（`21, '张三'`）。**但是，** 因为是 `>` (范围查询)，索引的定位功能**到此为止**。MySQL 必须**扫描从 `age=21` 开始到索引末尾的所有记录**。如果表里 `age > 20` 的人占了 80%，这就相当于扫描了 80% 的索引。
    2.  **`AND name = '张三'` (过滤)：**
        在 `age > 20` 的这个**巨大**的“扫描范围”内 (21, '张三'), (25, '李四'), ..., (50, '张三')，`name` 字段是**无序**的（它只在 *同一个 age* 内部有序）。
        MySQL 别无选择，只能对扫描到的**每一条**记录，都**逐一**检查其 `name` 是否等于 '张三'。这个操作在 `EXPLAIN` 的 `Extra` 字段里通常显示为 **`Using where`**。

* **效率总结：** `大范围扫描 (age)` + `逐条过滤 (name)`。效率极低。

---

### 结论：为什么“糟糕”？

我们用一个比喻来总结：

**查询任务：** 在字典里（索引）找出所有“拼音以 `z` 开头 (name)，且是 3 画 (age)”的字。

* **A. `(name, age)` 索引 (拼音, 笔画)：**
    我先翻到 `Z` 部首（`name = '张三'`，**精确定位**），`Z` 部首下的字本来就不多。我再在 `Z` 部首里按笔画数（`age > 20`，**小范围扫描**）找到 3 画的字。**这很快。**

* **B. `(age, name)` 索引 (笔画, 拼音)：**
    我先翻到“3 画”部首 (`age > 20`，**范围扫描**，假设 3 画以上的字占了字典的 80%）。然后我**被迫一页一页地翻看这 80% 的内容** (`Using where` 过滤)，找出其中拼音以 `z` 开头的字。**这太慢了。**

这就是为什么我们说 `(age, name)` 索引对于这个查询来说是“糟糕”的，以及为什么**“等值查询 (`=`) 的列”** 应该永远放在 **“范围查询 (`>`) 的列”** 之前。
