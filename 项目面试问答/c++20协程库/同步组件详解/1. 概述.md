### 整体设计哲学

在开始深入每个组件之前，我们可以先总结一下这个模块的整体设计哲学，这能让你在面试的开头就展现出对项目宏观设计的把握：

1.  **基于协程的异步化**：所有的同步原语都是为协程设计的，它们不会阻塞操作系统线程。当一个协程需要等待时，它会`co_await`一个同步原语，然后挂起自身，将执行权交还给调度器（`scheduler`），调度器可以去执行其他就绪的协程。这大大提高了线程的利用率，特别适合于高并发的I/O密集型场景。
2.  **统一的 Awaiter 模式**：每个同步原语都遵循了C++20协程的 Awaiter 模式。它们都提供了一个返回 `awaiter` 对象的方法（如 `lock()`, `wait()`）。这个 `awaiter` 对象实现了 `await_ready`, `await_suspend`, `await_resume` 三个关键方法，来控制协程的挂起和恢复流程。
3.  **与调度器的紧密集成**：同步原语的实现与 `context` 和 `scheduler` 紧密相关。当一个协程被挂起时，它会将自己的句柄（`coroutine_handle`）保存在 `awaiter` 中。当等待的条件满足时，另一个协程或操作会通过 `context` 的 `submit_task` 方法，将被挂起的协程重新提交给调度器，使其有机会被再次执行。
4.  **性能导向的原子操作**：在底层实现上，大量使用了 `std::atomic` 和精细的内存序（memory ordering）来保证线程安全和无锁化（或尽可能减少锁的粒度），这体现了对高性能并发编程的深入理解。

现在，我们来逐个分析每个同步组件。

### 1. `mutex` (互斥锁)

* **文件**: `include/coro/comp/mutex.hpp`, `src/comp/mutex.cpp`

* **目的**：提供协程安全的互斥访问，保证在同一时间只有一个协程能进入临界区。

* **核心实现**：
    1.  **状态管理 (`m_state`)**: `mutex` 的核心是一个原子变量 `std::atomic<awaiter_ptr> m_state`。这个状态有三种可能：
        * `nolocked`: 一个特殊值（非零），表示锁未被持有。
        * `locked_no_waiting`: `nullptr` (0)，表示锁已被持有，但没有其他协程在等待。
        * 其他指针值: 表示锁已被持有，并且该指针指向一个由 `mutex_awaiter` 组成的**单向链表**的头部，这个链表就是等待队列。
    2.  **`lock()` 方法**: `lock()` 方法并不直接加锁，而是返回一个 `mutex_awaiter` 对象。
    3.  **`mutex_awaiter` 的工作流程**:
        * `await_ready()`: 总是返回 `false`，表示需要进入 `await_suspend` 尝试挂起。
        * `await_suspend(handle)`: 这是关键。它会进入一个 `while(true)` 循环，使用 `compare_exchange_weak` (CAS) 操作来尝试获取锁：
            * **情况A：锁是 `nolocked`**：尝试将 `m_state` 从 `nolocked` 交换为 `locked_no_waiting`。如果成功，说明获得了锁，`await_suspend` 返回 `false`，协程不会被挂起，继续执行。
            * **情况B：锁已被持有**：将当前的 `awaiter` 插入到等待链表的头部。它会读取当前的 `m_state` (即链表头)，将自己的 `m_next` 指向它，然后尝试用自己的地址去替换 `m_state`。如果成功，`await_suspend` 返回 `true`，当前协程被挂起。
        * `await_resume()`: 当协程最终被唤醒并恢复执行后，会调用此方法。这里主要是做一些清理工作，比如调用 `m_ctx.unregister_wait()`。
    4.  **`unlock()` 方法**:
        * 首先，它会检查是否有协程在等待。它会用一个 `nullptr` 去 `exchange` `m_state`，从而“截断”整个等待链表。
        * 然后，它会**反转**这个等待链表。这是因为 CAS 操作使得等待者形成了一个栈（后进先出）。为了公平性（或者说为了处理方便），`unlock` 时将这个栈反转成一个队列。
        * 最后，它会取出反转后链表的头一个 `awaiter` (也就是最早等待的那个协程)，调用它的 `resume()` 方法，这个方法会把协程的 `handle` 重新提交给调度器。这个被唤醒的协程将持有锁。

* **面试亮点**:
    * 可以详细解释 `m_state` 的三种状态以及如何使用 CAS 操作实现一个高效的、对调度器友好的互斥锁。
    * `unlock` 操作中的链表反转是一个值得注意的细节，它将 LIFO（后进先出）的等待队列转换成 FIFO（先进先出），虽然实现上更复杂一点，但避免了某些协程饿死（starvation）的可能性。
    * 强调它与 `std::mutex` 的根本不同：它不阻塞线程，只是挂起协程。

### 2. `condition_variable` (条件变量)

* **文件**: `include/coro/comp/condition_variable.hpp`, `src/comp/condition_variable.cpp`

* **目的**：配合 `mutex` 使用，允许协程等待某个条件成立。

* **核心实现**:
    1.  **等待队列**: `condition_variable` 内部维护一个由 `cv_awaiter` 组成的队列（有 `m_head` 和 `m_tail` 指针），并用一个 `spinlock` (`m_lock`) 来保护这个队列的并发访问。
    2.  **`wait(mutex& mtx, ...)`**: 返回 `cv_awaiter`。
    3.  **`cv_awaiter` 的工作流程**:
        * `await_suspend(handle)`:
            * 它可以接受一个可选的 `cond_type` 谓词函数。如果谓词存在且返回 `true`，那么 `await_suspend` 直接返回 `false`，协程不挂起（这被称为"spurious wakeup"的优化）。
            * 如果需要等待，它会先把自己加入到 `condition_variable` 的等待队列中。
            * **关键一步**：在协程挂起之前，它会调用 `m_mtx.unlock()` **释放**传入的互斥锁。这是 `condition_variable` 的标准行为，防止死锁。
            * 返回 `true`，协程挂起。
    4.  **`notify_one()` / `notify_all()`**:
        * `notify_one` 从等待队列头部取出一个 `awaiter`。
        * `notify_all` 取出整个队列。
        * 然后对这些取出的 `awaiter` 调用 `wake_up()` 方法。
    5.  **`wake_up()` 过程**:
        * 被唤醒的 `cv_awaiter` 在它的 `wake_up()` 方法中，**并不会立即恢复协程**。
        * 它会先尝试重新获取之前释放的那个 `mutex`。这一步是通过调用 `mutex_awaiter::register_lock()` 实现的。
        * 只有当它成功获取到 `mutex` 后，才会调用 `resume()` (最终调用 `m_ctx.submit_task`) 来让调度器恢复对应的协程。
        * `await_resume()` 在协程恢复后被调用，它会重新持有锁。

* **面试亮点**:
    * 讲解“等待-释放锁-挂起”和“唤醒-获取锁-恢复”的经典 `condition_variable` 工作流程是如何在协程中实现的。
    * 解释谓词（predicate）在 `wait` 中的作用：避免伪唤醒（spurious wakeups）导致的无效操作，提高效率。
    * 指出这里的 `condition_variable` 内部使用了 `spinlock`，可以讨论其与 `mutex` 的适用场景差异（`spinlock` 适用于锁持有时间极短的场景）。

### 3. `channel` (通道)

* **文件**: `include/coro/comp/channel.hpp`

* **目的**：提供一个协程安全的数据交换通道，是协程间通信（CSP模型）的核心组件。

* **核心实现**:
    1.  **组成**: `channel` 内部由一个 `mutex`，两个 `condition_variable` (`m_producer_cv` 和 `m_consumer_cv`)，以及一个数据缓冲区（`std::array` 或 `std::optional`）组成。
    2.  **模板特化**:
        * `channel<T, 0>`: 无缓冲通道。`send` 操作会一直等待，直到有 `recv` 操作来取数据。`full()` 和 `empty()` 直接通过 `m_data.has_value()` 判断。
        * `channel<T, capacity>` (capacity是2的幂): 有缓冲通道，使用位运算 `& (capacity - 1)` 来实现高效的环形队列索引。
        * `channel<T, capacity>` (通用版本): 有缓冲通道，使用标准的取模运算 `%` 来实现环形队列。
    3.  **`send(value)`**: 这是一个 `task<bool>` 协程。
        * 获取互斥锁 `m_mtx`。
        * `co_await m_producer_cv.wait(m_mtx, [this]{ return !full() || part_closed(); });`：如果通道已满，就在 `m_producer_cv` 上等待，直到有空间或通道被关闭。
        * 将数据放入缓冲区。
        * 调用 `m_consumer_cv.notify_one()` 唤醒一个可能在等待数据的消费者。
    4.  **`recv()`**: 这是一个 `task<std::optional<T>>` 协程。
        * 获取互斥锁 `m_mtx`。
        * `co_await m_consumer_cv.wait(m_mtx, [this]{ return !empty() || part_closed(); });`：如果通道为空，就在 `m_consumer_cv` 上等待，直到有数据或通道被关闭。
        * 从缓冲区取出数据。
        * 调用 `m_producer_cv.notify_one()` 唤醒一个可能在等待空间的生产者。
    5.  **`close()`**: 设置关闭状态，并 `notify_all` 两个条件变量，以唤醒所有等待的生产者和消费者。被唤醒的协程会检查关闭状态并优雅地退出。

* **面试亮点**:
    * 解释不同容量（0, 2的幂, 其他）的 `channel` 特化是如何实现的，以及这样做的性能考量。
    * 清晰地描述 `send` 和 `recv` 是如何使用 `mutex` 和 `condition_variable` 协同工作的，这是一个展示你对经典并发模型（生产者-消费者）理解的好机会。
    * 讨论 `close` 机制的重要性，以及它如何实现优雅的关闭和资源释放。

### 4. `event`, `latch`, `wait_group`

这三个组件可以放在一起看，因为它们都代表了不同模式的“等待-通知”机制。

* **`event` (事件)**
    * **文件**: `include/coro/comp/event.hpp`, `src/comp/event.cpp`
    * **目的**: 一个简单的信令机制。一个协程可以等待一个 `event`，另一个协程可以 `set` 这个 `event` 来唤醒所有等待者。
    * **实现**: 类似 `mutex`，用一个 `std::atomic<awaiter_ptr> m_state`。`nullptr` 表示未触发，`this` 指针表示已触发。`wait()` 的 `awaiter` 会在 `await_suspend` 中把自己加入等待链表。`set()` 会原子地将状态设为 `this`，并遍历唤醒整个等待链表上的协程。
    * **特点**: 一旦被 `set`，就永远是 `set` 状态。所有后续的 `wait` 都不会挂起。这是典型的“广播”模式。

* **`latch` (门闩)**
    * **文件**: `include/coro/comp/latch.hpp`
    * **目的**: 允许一个或多个协程等待，直到一个计数器减到零。
    * **实现**: 非常巧妙地**组合**了 `event` 和 `std::atomic<std::int64_t>`。
        * 构造时传入一个计数值。
        * `count_down()`: 原子地递减计数。当计数器减到1或更少时（使用 `fetch_sub`），它就调用内部 `event` 的 `set()` 方法。
        * `wait()`: 直接返回内部 `event` 的 `wait()` `awaiter`。
    * **特点**: 一次性使用。非常适合“主协程等待N个子任务完成”的场景。

* **`wait_group` (等待组)**
    * **文件**: `include/coro/comp/wait_group.hpp`, `src/comp/wait_group.cpp`
    * **目的**: 类似于 Go 语言的 `sync.WaitGroup`，可以动态地增减任务计数，并等待所有任务完成。
    * **实现**: 与 `event` 类似，使用原子计数器 `m_count` 和一个指向 `awaiter` 链表的原子指针 `m_state`。
        * `add(n)`: 增加计数。
        * `done()`: 减少计数。当计数变为0时，取出整个等待链表并唤醒所有等待的协程。
        * `wait()`: 如果计数不为0，则挂起并加入等待链表。
    * **特点**: 相比 `latch` 更加灵活，可以在运行时动态调整计数值。

* **面试亮点**:
    * **组件组合**: 重点讲解 `latch` 是如何通过组合 `event` 和 `atomic` 来实现的，这展示了良好的软件设计能力。
    * **场景辨析**: 能够清晰地说出 `event`, `latch`, 和 `wait_group` 的应用场景差异：
        * `event`: 简单的“开始”或“完成”信号广播。
        * `latch`: 等待固定数量的一次性事件完成。
        * `wait_group`: 等待可变数量的、可能在运行时动态增减的事件完成。
    * **与 Go 语言对比**: 如果面试官熟悉 Go，可以将 `wait_group` 和 `channel` 与 Go 的相应原语进行对比，这会是一个很好的加分项。
