### 1\. C++20 协程的核心三要素

在深入代码之前，我们必须先理解 C++20 协程的三个核心组件，因为 `task` 类的设计完全是围绕它们构建的：

1.  **协程句柄 (`std::coroutine_handle<P>`)**: 这是一个轻量级的、不持有任何资源的句柄（类似于裸指针），指向协程的状态机（协程帧）。通过它可以 `resume()` (恢复) 或 `destroy()` (销毁) 协程。
2.  **Promise 对象**: 每个协程帧内部都包含一个由编译器自动生成的 `promise` 对象。它是协程**内部**与**外部**沟通的桥梁。它可以存储协程的返回值或异常，并且可以决定协程在启动和结束时的行为（是否挂起）。
3.  **协程返回类型 (Return Type)**: 这就是我们在协程函数签名中指定的返回类型，在本项目中就是 `coro::task<T>`。这个返回类型对象通常会持有一个协程句柄，从而管理协程的生命周期。

`task.hpp` 的使命就是将这三者有机地结合起来，提供一个安全、易用的协程抽象。

### 2\. `coro::task<T>` 的剖析

`task` 是用户直接交互的接口，它代表一个可能尚未完成的异步计算任务。

#### 2.1. 角色与职责

`task` 类在设计上扮演了 **RAII (资源获取即初始化)** 的角色，它负责管理协程帧的生命周期。

  * **持有句柄**: `task` 类的核心成员是一个协程句柄 `m_coroutine`。
  * **生命周期管理**:
      * 当一个 `task` 对象被创建时，它就获得了协程帧的所有权。
      * 当 `task` 对象被销毁时，它的析构函数会调用 `m_coroutine.destroy()` 来释放协程帧占用的内存。
      * 它是一个**移动专属 (Move-Only)** 类型，禁止了拷贝构造和拷贝赋值，确保了任何时候只有一个 `task` 对象拥有对特定协程帧的所有权，避免了重复释放的问题。

#### 2.2. `detach()`: "发射后不管" 的任务

`task` 提供了一个重要的 `detach()` 方法。它的作用是：

1.  在 `promise` 对象中设置一个状态 `coro_state::detach`。
2.  将 `task` 对象内部的 `m_coroutine` 句柄置为 `nullptr`。

这样一来，当 `task` 对象本身被销毁时，由于其句柄已经是 `nullptr`，它就不会去 `destroy()` 协程帧了。协程帧的销毁责任被转移了。那么谁来销毁呢？答案是调度器 (`engine`)。当 `engine` 执行完一个协程，发现它是 `done()` 状态时，会调用全局的 `clean()` 函数。`clean()` 函数会检查 `promise` 的状态，如果是 `detach`，它就会负责调用 `handle.destroy()`。

**面试官可能会问**:

> `detach` 有什么应用场景？

**回答思路**:
`detach` 主要用于“fire-and-forget”的场景。例如，一个服务器接收到一个连接后，为这个连接创建一个新的协程去处理。主协程不关心这个连接处理协程的结果，它只想立即返回去接收下一个连接。这时就可以在新协程对应的 `task` 上调用 `detach()`，然后主协程就可以丢弃这个 `task` 对象了。新协程会由调度器在后台执行，执行完毕后由调度器负责清理资源。

### 3\. `promise` 对象的深度解析

`promise` 是 `task` 模块的“幕后黑手”，它控制着协程的关键行为，并作为 `task` 对象与协程内部状态沟通的桥梁。

#### 3.1. `initial_suspend`: 懒启动的奥秘

```cpp
constexpr auto initial_suspend() noexcept { return std::suspend_always{}; }
```

这是 `sheepcoro` 实现**懒启动 (Lazy Start)** 或**冷启动 (Cold Start)** 的关键。当一个协程函数被调用时，它的代码**不会立即执行**。它会先创建协程帧，然后检查 `initial_suspend` 的返回值。因为这里返回的是 `std::suspend_always`，所以协程在执行任何代码之前会立即挂起。控制权立刻返回给调用者，调用者得到一个 `task` 对象。这个 `task` 对象就像一个“启动器”，只有当调度器在稍后的某个时间点对这个 `task` 的句柄调用 `resume()` 时，协程的真正逻辑才会开始执行。

这种设计对于需要将任务提交到调度器的场景至关重要。

#### 3.2. `final_suspend` 与 `m_continuation`: 协程链式调用的核心

当一个协程执行完毕（无论是正常结束还是因异常终止），它会进入 `final_suspend`。这里的实现非常精妙：

```cpp
struct final_awaitable
{
    // ...
    template<typename promise_type>
    auto await_suspend(std::coroutine_handle<promise_type> coroutine) noexcept -> std::coroutine_handle<>
    {
        auto& promise = coroutine.promise();
        return promise.m_continuation != nullptr ? promise.m_continuation : std::noop_coroutine();
    }
    // ...
};

auto final_suspend() noexcept -> final_awaitable { return {}; }
```

`final_suspend` 返回一个自定义的 `final_awaitable` 对象。当协程结束并挂起时，C++运行时会调用这个 `awaitable` 对象的 `await_suspend` 方法。

  * **`m_continuation`**: 这是一个 `std::coroutine_handle<>` 成员，它存储了**正在等待**当前协程 (`co_await` 当前 `task`) 的那个协程的句柄。
  * **链式唤醒**: `await_suspend` 的逻辑是：如果 `m_continuation` 不是 `nullptr`，就返回它。C++ 运行时会自动 `resume()` 这个返回的句柄。这就实现了当一个任务 A 完成后，自动唤醒正在 `co_await` 它的任务 B 的效果。
  * 如果 `m_continuation` 是 `nullptr` (意味着没有其他协程在等待它)，则返回 `std::noop_coroutine()`，这是一个空操作的协程句柄，协程就此安静地结束并保持在最终挂起状态，等待 `task` 的析构函数来销毁它。

#### 3.3. 结果与异常处理

  * **返回值**: 对于 `task<T>`，`promise<T>` 继承自一个 `container<T>`，它内部使用 `std::variant` 或类似机制来存储 `co_return` 的值。
  * **void 返回值**: 对于 `task<void>`，`promise<void>` 特化版本有一个 `return_void()` 方法。
  * **异常**: 不论是哪个版本，`promise` 都有一个 `unhandled_exception()` 方法。当协程内部有未捕获的异常抛出时，这个方法会被调用，它会通过 `std::current_exception()` 捕获异常并将其存入 `promise` 对象中 (例如存在 `m_exception_ptr` 里)。当其他协程 `co_await` 这个 `task` 并调用 `await_resume` 时，`promise` 的 `result()` 方法会检查这个异常指针，如果存在，就 `std::rethrow_exception`，将异常传播出去。

### 4\. `co_await` 一个 `task` 的完整流程

现在，我们把所有部分串联起来，看看 `auto result = co_await some_task;` 这行代码背后发生了什么。

假设协程 B 正在执行，遇到这行代码，其中 `some_task` 是协程 A 返回的 `task` 对象。

1.  **`operator co_await()`**: `some_task.operator co_await()` 被调用，它返回一个 `awaitable` 对象。这个对象持有了协程 A 的句柄。

2.  **`await_ready()`**: 运行时调用 `awaitable` 的 `await_ready()`。如果协程 A 已经执行完毕 (`.done()`)，`await_ready` 返回 `true`，协程 B 就不会挂起，直接进入第 4 步。通常情况下，任务尚未完成，返回 `false`。

3.  **`await_suspend()`**: 运行时调用 `awaitable` 的 `await_suspend(coro_b_handle)`。

      * 在 `await_suspend` 内部，协程 B 的句柄 `coro_b_handle` 被赋值给协程 A 的 `promise` 对象的 `m_continuation` 成员。这就像是 B 对 A 说：“你执行完后记得叫我”。
      * 然后 `await_suspend` 返回协程 A 的句柄。
      * 这个返回值告诉运行时：“请挂起当前的协程 B，并立即 `resume()` 协程 A”。

4.  **执行与完成**: 协程 A 开始或继续执行。当它执行完毕，进入 `final_suspend`。如前所述，`final_awaitable` 的 `await_suspend` 会返回之前保存的 `m_continuation`，也就是协程 B 的句柄。

5.  **`await_resume()`**: 协程 B 被唤醒后，运行时会调用 `awaitable` 的 `await_resume()`。这个函数会访问协程 A 的 `promise` 对象，通过调用 `promise().result()` 获取返回值或重新抛出异常。这个返回值最终被赋给 `result` 变量。

至此，一次完整的协程切换与协作流程就完成了。

### 总结

`sheepcoro` 的 `task` 模块是一个设计精良的 C++20 协程封装。它通过以下几个关键设计，构建了一个强大而灵活的异步编程基础：

  * **RAII风格的 `task` 类**：简化了协程生命周期管理，避免了手动 `destroy()` 句柄的麻烦和风险。
  * **`std::suspend_always` 的 `initial_suspend`**：实现了协程的懒启动，将执行控制权完全交给调度器。
  * **`continuation` 机制**：通过在 `promise` 中保存等待者的句柄，并在 `final_suspend` 中返回它，巧妙地实现了协程之间的无缝链式唤醒。
  * **`detach()` 语义**：为“发射后不管”类型的任务提供了清晰的生命周期管理方案，将资源回收的责任安全地转移给调度器。
