好的，这个 `sheepcoro` 项目是一个基于 C++20 协程和 io_uring 的高性能网络库。为了让你在面试中能够深入地回答相关问题，我将为你详细讲解其中的重点模块。

### 核心模块概览

该项目的核心可以分为以下几个部分：

1.  **协程封装 (`task.hpp`)**: 这是整个协程框架的基石，定义了协程的创建、执行和销毁。
2.  **调度器 (`scheduler.hpp`, `scheduler.cpp`)**: 负责在多个线程中分发和执行协程任务。
3.  **执行引擎 (`engine.hpp`, `engine.cpp`)**: 实际执行协程，并与 `io_uring` 交互，处理异步 I/O 事件。
4.  **同步原语**:
    * **`mutex.hpp`, `mutex.cpp`**: 提供了协程安全的互斥锁。
    * **`condition_variable.hpp`, `condition_variable.cpp`**: 提供了协程安全的条件变量。
5.  **网络库 (`tcp.hpp`, `tcp.cpp`)**: 基于 `io_uring` 封装了 TCP 网络通信相关的操作，例如 `accept`, `read`, `write`, `connect` 等。

---

### 1. 协程封装 (`task.hpp`)

`task.hpp` 是对 C++20 `std::coroutine_handle` 的一层封装，旨在提供更易于使用的协程对象。

* **`task<T>` 类**:
    * 这是用户直接使用的协程对象类型。`T` 是协程的返回值类型，`void` 表示无返回值。
    * 它持有一个 `coroutine_handle`，这是指向协程状态的句柄。
    * 提供了 `co_await` 操作符重载，使得一个 `task` 可以被另一个协程等待。
    * **关键点**:
        * **所有权转移**: `task` 对象在移动构造和移动赋值时会转移 `coroutine_handle` 的所有权，确保协程状态不会被意外地多次销毁。
        * **`detach()`**: 调用 `detach()` 会分离协程句柄，使得 `task` 对象销毁时不会销毁协程状态。这通常用于“fire-and-forget”类型的任务，即任务被提交给调度器后就不再关心其结果。

* **`promise_type`**:
    * 每个协程都关联一个 `promise` 对象，用于协程与外部的通信。
    * `get_return_object()`: 创建并返回与该 `promise` 关联的 `task` 对象。
    * `initial_suspend`: 返回 `std::suspend_always`，表示协程在启动后立即挂起，将控制权交还给调用者（或调度器）。这是协程库实现调度的关键。
    * `final_suspend`: 协程执行完毕后，通过 `final_awaitable` 来处理后续逻辑。如果设置了 `m_continuation`，则会恢复执行“续体”（continuation），也就是 `co_await` 该 `task` 的另一个协程。
    * `unhandled_exception`: 用于捕获协程中未处理的异常。

**面试官可能会问**:

> 这个 `task` 和 `std::coroutine_handle` 有什么区别？为什么不直接使用 `coroutine_handle`？

**回答思路**:

`std::coroutine_handle` 是一个相对底层的句柄，直接使用它需要手动管理协程的生命周期，容易出错。`task` 类通过 RAII (Resource Acquisition Is Initialization) 的思想，将协程的生命周期与 `task` 对象的生命周期绑定，简化了资源管理。同时，`task` 封装了 `co_await` 的逻辑，使得协程间的协作更加自然。

### 2. 调度器 (`scheduler.hpp`, `scheduler.cpp`)

调度器负责管理一个或多个线程（`context`），并将协程任务（`task`）分发给这些线程执行。

* **`scheduler` 类**:
    * **单例模式**: 通过 `get_instance()` 获取全局唯一的调度器实例。
    * **`init(ctx_cnt)`**: 初始化调度器，创建 `ctx_cnt` 个 `context`（通常等于 CPU核心数）。
    * **`loop()`**: 启动所有 `context` 的事件循环，并等待它们结束。
    * **`submit(handle)`**:
        * 这是向协程框架提交任务的入口。
        * 它通过 `m_dispatcher` 选择一个 `context`。
        * 然后调用该 `context` 的 `submit_task()` 将任务提交到其工作队列中。

* **`dispatcher` 类 (`dispatcher.hpp`)**:
    * 这是一个策略类，用于决定新提交的任务应该被分发到哪个 `context`。
    * 项目中实现了 `round_robin`（轮询）策略，将任务依次分发给每个 `context`，以实现负载均衡。

**面试官可能会问**:

> 这个项目是如何实现多线程调度的？如何保证线程安全？

**回答思路**:

该项目采用的是典型的 **M:N 调度模型**，即 M 个协程在 N 个线程上调度。

1.  **调度器 (`scheduler`)** 管理一个线程池，每个线程对应一个 `context` 对象。
2.  每个 `context` 内部都有一个自己的 `engine` 和一个用于接收新任务的 **多生产者-多消费者（MPMC）无锁队列** (`m_task_queue` in `engine.hpp`)。
3.  当外部通过 `scheduler::submit()` 提交任务时，`dispatcher` 会选择一个 `context`，然后将协程句柄 push 到该 `context` 对应 `engine` 的无锁队列中。
4.  由于 `m_task_queue` 是线程安全的 `AtomicQueue`，所以从不同线程提交任务是安全的。每个 `engine` 在自己的线程中从队列里 `pop` 任务并执行，避免了任务执行过程中的竞争。

### 3. 执行引擎 (`engine.hpp`, `engine.cpp`)

`engine` 是每个工作线程的 "心脏"，它负责：
1.  从任务队列中取出并执行协程。
2.  与 `io_uring` 交互，提交 I/O 请求。
3.  等待并处理 `io_uring` 的完成事件。

* **`m_upxy` (`uring_proxy`)**: `io_uring` 的代理类，封装了 `io_uring` 的初始化、提交（SQE）、等待和获取完成事件（CQE）等操作。

* **核心流程**:
    1.  **`exec_one_task()`**: 从 `m_task_queue` 中弹出一个协程句柄 (`schedule()`)，然后调用 `handle.resume()` 执行它。
    2.  **遇到 I/O 操作**: 当协程执行到 I/O 操作时（例如 `co_await tcp_connector.read(...)`），它会：
        * 通过 `get_free_urs()` 从 `io_uring` 获取一个可用的 SQE (Submission Queue Entry)。
        * 填充 SQE，例如设置为 `read` 操作，并附带上文件描述符、缓冲区等信息。
        * **关键**: 将当前协程的 `coroutine_handle` 作为 `user_data` 关联到这个 SQE 上。
        * 协程挂起，将控制权交还给 `engine`。
    3.  **`poll_submit()`**: 这是 `engine` 的事件循环核心。
        * **`do_io_submit()`**: 将所有待提交的 I/O 请求（SQEs）一次性提交给内核 (`m_upxy.submit()`)。
        * **`m_upxy.wait_eventfd()`**: 阻塞等待，直到有 I/O 完成或有新任务通过 `wake_up()` 被唤醒。
        * **`peek_batch_cqe()`**: 从完成队列（CQE）中批量获取已完成的事件。
        * **`handle_cqe_entry()`**:
            * 对于每个完成事件（CQE），通过 `io_uring_cqe_get_data()` 取出之前设置的 `user_data`，这里就是 `io_info` 指针。
            * 调用 `data->cb()`，这个回调函数通常会重新将协程句柄 `submit_task` 到任务队列中，使其可以继续执行。

* **`wake_up()`**:
    * 当其他线程向当前 `engine` 的任务队列提交新任务时，会调用 `wake_up()`。
    * 它通过向 `eventfd` 写入一个值来唤醒可能因等待 I/O 而在 `m_upxy.wait_eventfd()` 阻塞的 `engine` 线程，使其能及时处理新任务。

**面试官可能会问**:

> io_uring 在这里起到了什么作用？相比 epoll 有什么优势？

**回答思路**:

`io_uring` 是 Linux 内核提供的一套高性能异步 I/O 接口。

1.  **作用**: `engine` 通过 `io_uring` 提交读、写、接受连接等网络 I/O 请求，并在 I/O 操作完成后获得通知。
2.  **优势**:
    * **真正的异步**: `epoll` 本质上是同步阻塞的 I/O 多路复用，需要通过 `read/write` 系统调用来实际读写数据。而 `io_uring` 从提交请求到完成通知都是异步的，整个过程应用程序无需阻塞。
    * **减少系统调用**: `io_uring` 通过共享内存环形缓冲区（Submission Queue 和 Completion Queue）与内核交互。应用程序可以一次性提交多个 I/O 请求，内核处理完后也一次性返回多个完成事件，极大地减少了用户态和内核态之间的切换开销。
    * **零拷贝**: 在支持的硬件和内核版本上，`io_uring` 可以实现零拷贝，进一步提升性能。

### 4. 同步原语 (`mutex.hpp`, `condition_variable.hpp`)

在协程并发执行时，同样需要同步机制来保护共享资源。但不能使用标准库的 `std::mutex`，因为它会导致整个线程阻塞，而不是仅仅挂起当前协程。

* **`mutex` 类**:
    * **`lock()`**: 返回一个 `mutex_awaiter`。当 `co_await mutex.lock()` 时：
        * `await_suspend` 会尝试获取锁。
        * 如果锁未被占用，它会以原子方式将状态从未锁定（`nolocked`）更改为锁定（`locked_no_waiting`），然后立即返回（`await_suspend` 返回 `false`），协程继续执行。
        * 如果锁已被占用，它会将当前的 `mutex_awaiter` 添加到一个等待者链表中（通过原子地交换 `m_state` 指针），然后挂起协程（`await_suspend` 返回 `true`）。
    * **`unlock()`**:
        * 检查等待者链表。
        * 如果没有等待者，则原子地将状态改回 `nolocked`。
        * 如果有等待者，它会从链表中取出一个 `awaiter`，并通过 `to_resume->resume()` 将其对应的协程重新提交到调度器中执行。

* **`condition_variable` 类**:
    * **`wait(mutex& mtx)`**:
        * 返回一个 `cv_awaiter`。当 `co_await cv.wait(mtx)` 时，`await_suspend` 会：
            * 将当前 `awaiter` 添加到条件变量的等待队列中。
            * 调用 `mtx.unlock()` 释放锁。
            * 挂起当前协程。
    * **`notify_one()`**:
        * 从等待队列中取出一个 `awaiter`。
        * 调用其 `wake_up()` 方法。`wake_up` 会尝试重新获取 `mutex`，成功后将协程重新提交给调度器。

**面试官可能会问**:

> 为什么需要自己实现 `mutex` 和 `condition_variable`？它们的实现和标准库有什么不同？

**回答思路**:

标准库的同步原语是为线程设计的，当获取不到锁或等待条件不满足时，它们会**阻塞整个操作系统线程**。在协程模型中，一个线程上可能运行着成百上千个协程，如果一个协程阻塞了整个线程，其他所有在该线程上的协程都无法执行，这违背了协程高并发的初衷。

我们自己实现的版本是**协程感知**的：
* 当获取不到锁或需要等待时，它们只会**挂起当前的协程**，并将 CPU 的执行权交还给 `engine` 的事件循环。
* `engine` 可以继续执行其他就绪的协程或处理 I/O 事件，线程本身并不会被阻塞。
* 当锁被释放或条件满足时，`unlock` 或 `notify` 操作会将等待的协程重新放回调度器的就绪队列，等待下一次被调度执行。

### 5. 网络库 (`tcp.hpp`, `tcp.cpp`)

这一部分是 `io_uring` 和协程思想的具体应用。

* **`tcp_server`**:
    * 构造函数中完成 `socket`, `bind`, `listen` 等标准流程，并设置为非阻塞。
    * **`accept()`**:
        * 返回一个 `tcp_accept_awaiter`。
        * 当 `co_await server.accept()` 时，`await_suspend` 会向 `io_uring` 提交一个 `accept` 请求。
        * 协程挂起，等待新连接的到来。
        * 当 `engine` 处理完成事件时，会恢复该协程，其 `co_await` 表达式的返回值就是一个代表新连接的 `tcp_connector` 对象。

* **`tcp_connector`**:
    * 代表一个 TCP 连接。
    * **`read(buf, len)` / `write(buf, len)`**:
        * 分别返回 `tcp_read_awaiter` 和 `tcp_write_awaiter`。
        * `co_await` 它们时，会向 `io_uring` 提交读/写请求，并挂起协程。
        * 操作完成后协程被唤醒，`co_await` 表达式的返回值是实际读/写的字节数。

**面试官可能会问**:

> 请描述一下一个完整的 TCP echo server 的工作流程。

**回答思路**:

1.  在 `main` 函数中，初始化 `scheduler` 并启动 `loop`。
2.  创建一个 `task` 作为主协程，并用 `scheduler::submit` 提交它。
3.  在主协程中：
    * 创建一个 `tcp_server` 实例。
    * 进入一个 `while(true)` 循环。
    * 在循环中，`co_await server.accept()` 来等待新的客户端连接，这将返回一个 `tcp_connector`。
    * 对于每个新的 `connector`，创建一个新的 `task`（例如 `echo_session(connector)`）来处理这个连接，并用 `scheduler::submit` 或类似的机制提交这个新任务，然后主协程继续 `co_await server.accept()` 等待下一个连接。
4.  在 `echo_session` 协程中：
    * 进入一个 `while(true)` 循环。
    * 在循环中，`auto bytes_read = co_await connector.read(buffer, size)` 来异步读取数据。
    * 如果 `bytes_read` 大于 0，则 `co_await connector.write(buffer, bytes_read)` 将数据异步写回。
    * 如果 `bytes_read` 为 0 或小于 0，表示连接关闭或出错，退出循环。
    * 最后，`co_await connector.close()` 关闭连接。

这个流程充分利用了协程和异步 I/O 的优势：主协程不会因为等待连接而被阻塞，每个连接的处理协程也不会因为等待读写而被阻塞。成千上万的连接可以由少数几个线程高效地处理。
